# qr.menu

Сервис QR-меню для мини-заведений (кофейни, суши-студии, мини-кафе, бары).

## Дизайн-система

Визуальный стиль перенесён из референса `qr-menu-service/` (Next.js/v0-прототип, лежит в корне репозитория как справочный материал, в само приложение не подключается). Кремовый фон + терракотовый акцент, Playfair Display (заголовки) + Manrope (текст).

- `src/public/css/design-system.css` — все токены и переиспользуемые классы (`.btn`, `.card`, `.admin-shell`, `.public-menu` и т.д.).
- `src/public/css/fonts.css` + `src/public/fonts/*.woff2` — шрифты самохостятся (не с CDN). У оригинальных Fraunces/DM Sans нет кириллицы в Google Fonts — заменены на **Playfair Display** и **Manrope** (тот же характер, полная поддержка кириллицы).
- `src/views/partials/` — переиспользуемые куски вёрстки: `brand.ejs` (лого), `icon.ejs` (инлайн SVG-иконки), `admin-sidebar.ejs` / `admin-topbar.ejs` (каркас админки), `head-assets.ejs` (favicon + подключение CSS).
- Бренд-нейм сервиса — `qr.menu` (см. `src/config/constants.js`), в духе референса.

## Стек

- Node.js + Express
- EJS (серверный рендеринг)
- PostgreSQL + node-pg-migrate
- express-session + connect-pg-simple
- bcrypt, zod, multer + sharp, qrcode, nodemailer, telegraf (Telegram-бот, отдельный процесс)
- exceljs (экспорт аналитики в `.xlsx`, промт 3.2) — только для генерации файлов на сервере, парсинг чужих `.xlsx` в проекте не используется

## Запуск для разработки

1. Скопировать `.env.example` в `.env` и при необходимости поменять значения:

   ```
   cp .env.example .env
   ```

2. Поднять PostgreSQL через Docker:

   ```
   docker compose up -d
   ```

   Контейнер публикует Postgres на хостовом порту `5433` (а не стандартном `5432`), чтобы не конфликтовать с локально установленным PostgreSQL, если он у вас уже запущен. Это отражено в `.env.example`.

3. Установить зависимости:

   ```
   npm install
   ```

4. Прогнать миграции:

   ```
   npm run migrate:up
   ```

   Среди миграций — постоянный фикстур `/menu/demo` (заведение, категории и позиции), на который ссылается кнопка "Посмотреть демо" на лендинге. В отличие от `npm run seed` ниже, это не dev-скрипт: он выполняется в любом окружении вместе с обычными миграциями (включая продакшен), не создаёт учётных записей и ничего не печатает в консоль — так что демо-ссылка с главной страницы работает сразу после деплоя, без ручного шага.

5. (Опционально) засеять тестовые учётные записи для локальной разработки:

   ```
   npm run seed
   ```

   Скрипт идемпотентен — при повторном запуске просто пропустит уже существующие аккаунты. Создаёт вход в `/admin/login` (**только для локальной разработки**), привязывая `venue_admin` к постоянному фикстуру `demo` (см. шаг 4) — отдельное тестовое заведение больше не создаётся, demo полностью заменяет его в этой роли:

   | Логин | Пароль | Роль |
   |---|---|---|
   | `superadmin` | `superadmin123` | superadmin |
   | `venue_admin` | `venueadmin123` | venue_admin (заведение demo) |

6. Запустить сервер в режиме разработки (перезапуск при изменении файлов):

   ```
   npm run dev
   ```

7. Проверить, что сервер поднялся и подключился к БД:

   ```
   curl http://localhost:3000/health
   ```

   Должен вернуться `{"status":"ok","db":"connected"}`.

## Загрузка фото позиций меню

- Принимаются только изображения, максимум 8 МБ на файл.
- Оригинал с телефона никогда не сохраняется как есть — конвертируется в WebP в двух размерах: превью (200px по ширине) и полноразмерная версия (800px по ширине).
- При замене или удалении фото старые файлы удаляются с диска, "мусор" не копится.
- Битый файл (не читается как изображение) не роняет сервер — возвращается понятная ошибка.
- Важный порядок middleware в `src/app.js`: `uploadItemPhoto`/`uploadVenueImages` (multer) обязаны идти ДО `csrfProtection` в цепочке для `/admin/items` и `/admin/venue-settings`, а сами эти два маунта — раньше более общих `app.use('/admin', ...)` ниже (Express прогоняет middleware по префиксу пути в порядке регистрации, даже если у смонтированного роутера нет подходящего маршрута). `express.urlencoded`/`express.json` не трогают `multipart/form-data` — если `csrfProtection` окажется раньше multer или раньше этих двух специфичных маунтов, `req.body` на момент проверки CSRF-токена ещё пуст, и любая форма с файлом (создание/правка позиции, настройки заведения) получает 403 при каждой отправке.

## Публичная страница меню

- `GET /menu/:slug` — отрендеренная страница кэшируется в памяти процесса (`Map` + TTL 5 минут), ключ `slug:lang`.
- Кэш инвалидируется при любом сохранении категорий/позиций этого заведения в админке — правки видны на публичной странице сразу, без ожидания истечения TTL.
- Несуществующий `slug` → честный 404. Отключённое (`is_active=false`) заведение → страница "меню временно недоступно" с HTTP 200, без падения.
- Внизу — блок контактов (телефон `tel:`, адрес со ссылкой на 2GIS, соцсети), кнопка "Поделиться" (Web Share API с фолбэком на копирование ссылки в буфер) и футер "сделано на QR-Меню", который показывается только если у заведения включён `show_powered_by` (переключает суперадмин на `/superadmin/venues` — тарифов пока нет, поэтому этим управляет только он, не сам venue_admin).
- Контакты редактируются в `/admin/venue-settings` (только venue_admin), сохранение инвалидирует кэш этого заведения.

## Лендинг (`/`)

- `src/routes/landing.js` + `src/views/public/landing.ejs` — секции идут в порядке nav → hero → stats → «Возможности» (`#features`) → «Кому подходит» (`#for-whom`) → «Как это работает» (`#how`) → «Почему мы» (`#why`) → «Тарифы» (`#prices`) → FAQ (`#faq`) → финальный CTA (`#cta`) → футер.
- Весь текст — через `t('landing.…')` в `src/i18n/ru.json`/`uz.json`, включая демо-данные превью меню в hero-карточке (никакого текста хардкодом в шаблоне).
- Тариф: цены не хардкодятся в шаблоне — `PRICE_MONTH_UZS`, `PRICE_MONTH_OLD_UZS`, `FREE_TRIAL_MONTHS`, `DISCOUNT_PERCENT` в `src/config/constants.js`, форматирование (разряды через неразрывный пробел, суффикс `сум`/`so'm` по языку) — `formatPriceUZS()` в `src/utils/formatPrice.js`. Стоимость за 3 и 6 месяцев считается в роуте от тех же периодов подписки (`PERIOD_MONTHS` из `src/validators/paymentValidators.js`), отдельного списка периодов для лендинга нет.
- В `<head>` — три JSON-LD блока: `Organization`, `Product`+`Offer` (цена/валюта берутся из тех же констант) и `FAQPage`, у которого `mainEntity` строится из того же массива вопросов/ответов, что и видимый аккордеон — текст не дублируется.
- Бургер-меню на ширине до 900px — чистый JS без зависимостей, `src/public/js/landing.js`, подключается прямо в `landing.ejs` (не в общий `head-assets.ejs`, аналогично тому как `public-menu.js` подключается только в `menu.ejs`).
- Футер — данные из `site_settings` (см. ниже), любое незаполненное поле или пустая колонка целиком просто не рендерится.

## Настройки сайта (контакты владельца сервиса)

- Таблица `site_settings` хранит ровно одну строку (`id` с `CHECK (id = 1)`, сидируется миграцией) — контакты и тексты владельца сервиса для футера лендинга: `owner_name`, `phone`/`phone_extra`, `email`, `telegram_url`, `instagram_url`, `address_ru`/`address_uz`, `working_hours_ru`/`working_hours_uz`, `about_ru`/`about_uz`, `offer_url`, `privacy_url`. Это не относится к заведениям (`venues`) — `venue_admin` доступа к этим данным не имеет.
- `GET/POST /superadmin/site-settings` — доступно только `superadmin` (`src/routes/superadmin.js`, форма — `src/views/superadmin/site-settings.ejs`, валидация — `src/validators/siteSettingsValidators.js`). Сохранение пишется в лог действий (`entity_type = 'site_settings'`, без привязки к заведению — `admin_action_logs.venue_id` для таких записей `NULL`, `/superadmin/logs` показывает их через `LEFT JOIN`).
- `src/models/siteSettingsModel.js` — прямой доступ к БД. Лендинг ходит не в модель напрямую, а через `src/services/siteSettingsCache.js` — простой in-memory кэш без TTL (значение читается один раз и живёт в памяти процесса), который инвалидируется сразу после сохранения формы в суперадминке — правки в футере видны на лендинге без перезапуска сервера и без ожидания.
- Сразу после миграций таблица содержит пустую строку (все поля `NULL`) — лендинг с этим не падает, футер деградирует до минимального вида (логотип, ссылки на секции, копирайт), без пустых колонок и заглушек.

## Кэш меню и синхронизация между процессами

- Отрендеренный HTML страницы меню кэшируется в памяти процесса (`src/services/menuCache.js`, TTL 5 минут, ключ `slug:lang`) — как и раньше. Дополнительно у заведения есть счётчик `venues.menu_version`, который растёт при любом изменении, влияющем на публичную страницу (категории, позиции, фото, настройки заведения, рейтинг, `show_powered_by`).
- Инвалидация всегда идёт по `venue_id`, а не по `slug` (`menuCache.invalidate(venueId)`) — переименование заведения не оставляет "зависший" старый ключ в памяти.
- Веб-процесс и процесс Telegram-бота (появится в следующих промтах) — разные Node-процессы. Чтобы изменение в одном было видно другому: после того как `menu_version` вырос, `src/services/pgNotify.js` шлёт `NOTIFY menu_changed, '<venue_id>'` через Postgres (`pg_notify`, параметризованно); отдельное долгоживущее LISTEN-соединение в каждом процессе подхватывает это и сбрасывает свою локальную копию кэша. Все 11 мест в коде, где меняются категории/позиции/настройки заведения, вызывают единую точку входа — `pgNotify.publishMenuChange(venueId)` (bump + локальный сброс + NOTIFY), чтобы не разойтись.
- Если LISTEN-соединение обрывается, процесс переподключается сам (задержка растёт 1с → 2с → 4с … максимум 30с) и при каждом успешном (пере)подключении полностью очищает локальный кэш — события за время обрыва могли потеряться, доверять им нельзя.
- Это подстраховка сверх TTL, а не замена: даже если NOTIFY не дошёл, через 5 минут кэш протухнет сам.

## Очередь уведомлений (outbox)

- Таблица `notifications` (`src/models/notificationModel.js`) — общая очередь для Telegram- и email-уведомлений: ставит веб-процесс (продление подписки, заявки с сайта), забирает и отправляет воркер бота (`bot/worker/notifications.js`, см. раздел «Telegram-бот» ниже). Прямых HTTP-вызовов между процессами нет.
- `enqueue()` кладёт запись со статусом `pending`. `claimBatch(limit)` атомарно захватывает пачку через `FOR UPDATE SKIP LOCKED` (чтобы два воркера не взяли одну и ту же запись) и "арендует" её на 2 минуты вперёд по `scheduled_at` — если воркер упадёт, не вызвав `markSent`/`markFailed`/`markSkipped`, запись сама вернётся в пул после истечения аренды.
- Логика ретраев (5 попыток, задержки 1м/5м/15м/1ч, `skipped` без ретраев при заблокированном боте) реализована в воркере — подробности в разделе «Telegram-бот».
- Точки постановки в очередь: продление подписки суперадминистратором (`POST /superadmin/venues/:id/extend`, `email`-уведомление владельцу заведения), заявки на подключение с сайта (`POST /apply`, `template: 'lead_created'`, см. раздел «Заявки на подключение» ниже) и почасовой пересчёт статусов подписки (`bot/worker/scheduler.js`, см. «Жизненный цикл заведения и подписки») — заявки из Telegram-бота уведомляют владельца напрямую, без очереди, у процесса бота уже есть живое соединение с Bot API.
- `enqueue()` поддерживает необязательный `dedupKey` — `ON CONFLICT (dedup_key) WHERE dedup_key IS NOT NULL AND status <> 'failed' DO NOTHING` на уникальном партиальном индексе (см. миграцию `1787503500000_create-notifications`), так что повторный вызов с тем же ключом (например, при перезапуске процесса посреди почасового пересчёта) не создаёт вторую запись и не падает на ограничении уникальности.

## Почта

- `src/services/mailer.js` — обёртка над `nodemailer`, транспорт настраивается через `SMTP_*`/`MAIL_FROM*` в `.env`. Если SMTP не сконфигурирован, `send()` не падает — логирует предупреждение и возвращает `{ skipped: true }`, так что локальная разработка не требует поднятого почтового сервера.
- Письма собираются из EJS-шаблонов в `src/views/emails/*.ejs` поверх общего `layout.ejs` (шапка с названием сервиса, тело, футер с контактами из `site_settings`). Вёрстка — таблицы и инлайн-стили (единственное место в проекте, где инлайн-стили допустимы: почтовые клиенты не читают `<style>`/CSS-переменные), без внешних картинок и шрифтов — цвета дизайн-системы вписаны значениями.
- На проде для домена отправителя нужны настроенные SPF и DKIM — без них письма (в первую очередь восстановление пароля) с высокой вероятностью уйдут в спам, хотя технически всё будет работать исправно.

## Конфигурация окружения

- `src/config/env.js` валидирует переменные окружения при старте через zod. `DATABASE_URL` и `SESSION_SECRET` обязательны — без них процесс не стартует и печатает понятную ошибку вместо падения где-то на первом запросе. `SMTP_*`, `BOT_TOKEN`, `BOT_USERNAME`, `APP_BASE_URL` опциональны — их отсутствие только отключает зависящие функции (почту, бота, корректные ссылки в письмах и в кнопке привязки Telegram) и печатает предупреждение в лог.
- `APP_BASE_URL` — публичный адрес сервиса, нужен там, где нет `req` для сборки ссылки из заголовков (письма, сообщения бота). `BOT_USERNAME` — username бота без `@`, отдельно от `BOT_TOKEN`: нужен веб-процессу, чтобы собрать ссылку `t.me/<username>?start=...` (привязка Telegram, `/admin/password`) — веб-процесс не имеет соединения с Bot API и не может узнать его сам. Полный список переменных — в `.env.example`.

## Telegram-бот

Отдельный процесс (`bot/index.js`), не часть веб-приложения — свой пул к той же БД, свой lifecycle. Общий код (модели, `src/i18n`, `src/config/db.js`) переиспользуется напрямую, SQL в `bot/` не пишется — если модели не хватает метода, он добавляется в `src/models/*`.

```
npm run bot        # запуск
npm run bot:dev     # с перезапуском при изменении файлов
```

- **Режимы** — `BOT_MODE=polling` (по умолчанию, для разработки, ничего дополнительно не нужно) или `BOT_MODE=webhook` (для продакшена: поднимает свой Express на `BOT_PORT`, секретный путь из `BOT_WEBHOOK_SECRET`, регистрирует вебхук по `BOT_WEBHOOK_URL` и просит Telegram присылать заголовок `X-Telegram-Bot-Api-Secret-Token` — `bot.webhookCallback` из telegraf сверяет его константным сравнением и отбрасывает запрос без него). Без `BOT_TOKEN` процесс бота не стартует вообще (веб-приложение при этом работает как обычно, уведомления просто копятся в очереди).
- **Язык пользователя** — таблица `telegram_users` (`src/models/telegramUserModel.js`). При первом контакте угадывается из `ctx.from.language_code`, но подтверждается кнопками — сохранённое значение в таблице первично. Дальше меняется только через `/lang`.
- **Команды**: `/start` (для нового пользователя — сначала подтверждение языка, дальше сразу), `/help`, `/lang`. Для `OWNER_TELEGRAM_ID` (можно несколько через запятую) — `/stats` и `/pending`: показывают то, что уже есть в проекте (заведения, статус подписки, очередь `notifications`) — заявки на подключение и запросы на оплату появятся здесь после промтов 1.2/1.4, сейчас в ответе честная пометка об этом.
- **Сообщение не по команде** пересылается всем `OWNER_TELEGRAM_ID` с кнопкой-подсказкой; Reply на пересланное сообщение в Telegram уходит исходному пользователю от имени бота (сопоставление сообщение → пользователь — в памяти процесса, `bot/lib/supportBridge.js`, не переживает перезапуск).
- **Воркер очереди** (`bot/worker/notifications.js`) — раз в 10 секунд забирает пачку из `notifications` (`claimBatch`, см. раздел про outbox выше) и отправляет по каналу. Рендер контента по `template`+`payload` — `bot/templates/notifications.js`, неизвестный `template` сразу помечается `failed`, без ретраев. Telegram 403 → `skipped` + `telegram_users.is_blocked=true`; 429 → повтор через `retry_after` из ответа; сетевые ошибки и SMTP-сбои — по графику 1м/5м/15м/1ч, после 5 попыток — `failed`. Простой троттлер держит исходящие в пределах ограничений Telegram (~25/с глобально, не чаще раза в секунду в один чат).
- **Планировщик жизненного цикла** (`bot/worker/scheduler.js`) — почасовой пересчёт статусов подписки и напоминания, запускается и останавливается вместе с воркером очереди в том же процессе. Подробности — раздел «Жизненный цикл заведения и подписки».
- **Антифлуд**: не больше 20 обновлений в минуту с одного `telegram_id`, дальше молча игнорируется (без ответа «вы флудите» — это только удвоило бы трафик).
- **Надёжность**: обработчики не роняют процесс при ошибке (`bot.catch` + try/catch в воркере на каждую запись отдельно); необработанные `unhandledRejection` шлют алерт `OWNER_TELEGRAM_ID` с дедупликацией (не чаще раза в 15 минут на один и тот же текст ошибки); `SIGTERM`/`SIGINT` — новые задачи не забираются, текущие дожидаются, пул закрывается; два экземпляра под одним токеном — второй получает от Telegram 409 на polling, логирует и завершается, не крутится в ошибках.

## Заявки на подключение (funnel)

Два входа для заявки от потенциального заведения — веб-форма и сценарий в Telegram-боте, оба пишут в одну таблицу `leads` (`src/models/leadModel.js`) и приводят к одному и тому же одобрению/отклонению.

- **`GET/POST /apply`** (`src/routes/apply.js`, форма — `src/views/public/apply.ejs`, антиспам ниже) — публичная страница, доступна из лендинга. Валидация полей — `src/validators/leadValidators.js` (`applyFormSchema`), общая с ботом там, где применимо (нормализация телефона, список типов заведения). `GET /apply/thanks` — страница благодарности с кнопкой в Telegram-бота (`site_settings.telegram_url`, если заполнен).
- **Антиспам на `/apply`** — четыре независимых слоя: honeypot-поле `website` (скрыто CSS, а не `display:none`/`hidden`, чтобы боты, читающие только разметку, не отличали его от обычного поля), минимальное время заполнения (< 3с между рендером формы и отправкой — `form_rendered_at`, скрытое поле с таймстампом), рейтлимит `applyLimiter` (3/час/IP, `src/middlewares/rateLimit.js`) и `ip_hash` в `leads` — SHA-256 от IP с солью, ротирующейся раз в сутки (`SESSION_SECRET` + дата), чтобы хеш одного и того же адреса нельзя было сопоставить между разными днями, но заявки за один день — можно. Сработавший honeypot/тайминг не показывает отдельную ошибку — тихо редиректит на `/apply/thanks`, как при настоящей отправке, без создания записи и без уведомлений.
- **Сценарий бота** (`bot/scenes/applyLead.js`, `Scenes.WizardScene`, вход — кнопка «Подключить заведение» в `/start`) — те же поля, что в веб-форме, по одному на шаг, с кнопками «Назад»/«Отмена» на каждом (`scene.action`, не завязаны на номер шага) и карточкой подтверждения перед отправкой. После телефона, если находится необработанная веб-заявка с тем же номером, бот предлагает привязать её к текущему чату вместо повторной анкеты (`leadModel.findAttachableWebLeadByPhone`). Уже существующая активная заявка/заведение на этот `telegram_id` — сценарий не заводится, показывается статус.
- **Уведомление владельца о новой заявке** — с сайта идёт через очередь `notifications` (`template: 'lead_created'`, веб-процесс не держит соединения с Bot API), из бота отправляется напрямую (`bot/lib/leadNotify.js`), карточка с кнопками «Одобрить»/«Отклонить» и (если у заявителя есть `telegram_id`) «Написать заявителю» — переиспользует `supportBridge` из раздела про бота выше, отдельного механизма под это нет.
- **Одобрение/отклонение** — общий сервис `src/services/leadApproval.js`, вызывается и из кнопок бота (быстрое одобрение с автосгенерированными значениями), и из `/superadmin/leads` (там же значения можно поправить перед подтверждением). `approveLead` создаёт заведение в статусе `draft` (`is_active=false`) и админ-аккаунт заведения одной транзакцией; slug — транслитерация названия с проверкой уникальности (`src/utils/slugify.js` + `leadModel.generateUniqueSlug`), логин — последние 9 цифр телефона (с суффиксом при коллизии), пароль генерируется случайно (`src/utils/generatePassword.js`). Выдача доступа (принудительная смена пароля при первом входе, логин и пароль двумя отдельными сообщениями) — раздел «Доступ: пароли, восстановление, привязка Telegram» ниже. Что происходит с заведением дальше (публикация, триал, статусы) — раздел «Жизненный цикл заведения и подписки» ниже.
- **`processedBy: null`** — одобрение/отклонение из бота не привязано ни к какому `admins`-аккаунту (эта привязка — тоже промт 1.5), поэтому `admin_action_logs.admin_id` для таких строк `NULL` (миграция `alter-admin-action-logs-admin-id-nullable`, тот же приём, что раньше применили к `venue_id` для `site_settings`); `/superadmin/logs` показывает такие записи через `LEFT JOIN admins` с меткой «Бот» вместо логина.
- **`/superadmin/leads`** (`src/routes/superadminLeads.js`) — список с фильтром по статусу и поиском по названию/телефону (пагинация — тот же паттерн, что `/superadmin/logs`), детальная карточка с кнопками «Отметить: связались» / «Одобрить» / «Отклонить» (обязательная причина) / «Спам» и предупреждением, если на этот же телефон есть другая активная заявка (`leadModel.findOtherActiveByPhone`) — возможный дубль, решение остаётся за суперадмином. Бейдж с числом новых заявок в сайдбаре (`leadModel.countNew()`) виден на любой странице суперадминки, не только на самих заявках.

## Жизненный цикл заведения и подписки

`venues.status` (`draft` → `trial` → `active` ⇄ `grace` ⇄ `suspended` → `archived`) — единственный источник правды о том, что доступно заведению и что видят гости. Вся логика переходов — в `src/services/venueLifecycle.js`, используется и почасовым планировщиком, и веб-роутами; изменять статус напрямую SQL-запросом в обход `venueLifecycle.transitionStatus` не стоит — тогда `status_changed_at` и `venue_status_history` разойдутся с реальным статусом.

- **Статусы**: `draft` — меню не опубликовано, публичная страница отдаёт 404, админка работает полностью. `trial` — 30 бесплатных дней после публикации, даётся один раз (`trial_started_at` не перезаписывается повторным вызовом `publishVenue`, даже по ошибке). `active` — оплаченный период. `grace` — до 5 дней после истечения, меню ещё работает, в админке баннер. `suspended` — меню заменено страницей-заглушкой, редактирование заблокировано. `archived` — после 90 дней в `suspended`, страница отдаёт 410 Gone.
- **Публикация** — кнопка «Опубликовать меню» на дашборде (`POST /admin/publish`), доступна только из `draft`. Чеклист готовности (`venueLifecycle.checkPublishReadiness`: ≥1 категория, ≥3 позиции без учёта демо-данных, заполнены название и телефон) проверяется и в шаблоне, и повторно на сервере — чтобы не опубликовать пустое меню, если категорию удалили во второй вкладке, пока форма была открыта. Позиции с `is_demo=true` (см. «Онбординг» ниже) не считаются за реальные — если все позиции демонстрационные, отдельная причина отказа `all_demo`, а не общая «мало позиций».
- **Почасовой пересчёт** (`bot/worker/scheduler.js`, тот же процесс, что и воркер уведомлений) — идемпотентно сравнивает текущий статус с тем, что должен быть по `subscription_until`/`suspended_at` (`venueLifecycle.computeTargetStatus`), и переводит при расхождении. Все переходы пишутся в `venue_status_history` (`venue_id`, `from_status`, `to_status`, `reason`, `actor_admin_id` — `NULL` для переходов от планировщика, тот же приём, что и у `admin_action_logs.admin_id` для действий бота). Напоминания (за 7/3/1 день до окончания, в день истечения, на 3-й день `grace`, в момент `suspended`, за 7 дней до архивации) идут через общую очередь `notifications` с `dedupKey` на каждое конкретное событие — перезапуск процесса посреди пересчёта не приводит к повторной отправке.
- **Канал напоминаний** — `venueLifecycle.notifyVenue` выбирает канал по приоритету: Telegram, если у заведения привязан `owner_telegram_id` (раздел «Доступ» ниже), иначе email, иначе задача `manual_contact_needed` владельцу сервиса в Telegram — ровно так, как описано в исходном требовании («если нет ни email, ни Telegram — задача связаться вручную»).
- **Продление подписки суперадминистратором** (`POST /superadmin/venues/:id/extend`) — оплата всегда означает `active`, даже если до этого шёл триал или заведение было в `grace`/`suspended`/`archived` (`venueLifecycle.reviveToActiveIfNeeded`) — реальная оплата возвращает и из архива, см. «Оплата подписки» ниже про то же самое через `payment_claims`. Кэш меню отдельно инвалидировать не нужно: проверка `is_active`/`status` в `publicMenu.js` всегда идёт по свежим данным из БД раньше, чем код обращается к `menuCache`, так что статус-заглушка/живая страница переключаются сразу на следующий запрос без специального сброса.
- **Публичная страница по статусу** (`src/routes/publicMenu.js`) — `draft` неотличим от несуществующего slug (404) для всех, КРОМЕ владельца этого же заведения: `/admin/preview-menu` (промт 1.6, пункт чеклиста «Проверить меню») пускает залогиненного венью-админа на его собственный черновик с баннером «Предпросмотр» сверху, не считает это просмотром гостя и не трогает общий кэш меню — сверка строго по `session.admin.venueId === venue.id`, чужой draft всё ещё 404. `is_active=false` (ручной рубильник суперадмина) отдаёт ту же заглушку, что и `suspended` (200), причём работает поверх любого статуса, включая `archived`. `suspended` — заглушка, 200 (чтобы не портить индексацию — QR-коды уже напечатаны и висят на столах). `archived` — та же вёрстка, 410 Gone. Сама заглушка (`src/views/public/menu-unavailable.ejs`) показывает логотип, название, телефон, адрес и соцсети заведения — без единого намёка на причину недоступности.
- **Ограничения в админке** (`src/middlewares/venueStatusGate.js`, подключён к `/admin/categories`, `/admin/items`, `/admin/venue-settings`) — при `suspended` редиректит на `/admin/subscription` с пояснением, при `archived` — на дашборд (там баннер «архивировано» + ссылка «Написать в поддержку», если у сервиса заполнен `site_settings.telegram_url`). Действует на все HTTP-методы, не только GET — иначе прямой POST в обход интерфейса мог бы редактировать меню заблокированного заведения. Проверка всегда идёт по свежему статусу из БД, не из сессии: сессия живёт часами, а статус может смениться почасовым планировщиком в любой момент между запросами.
- **`/admin/subscription`** (`src/routes/adminSubscription.js`) — статус словами, дата окончания, дней осталось; полный экран оплаты (выбор периода, реквизиты, загрузка чека) описан в разделе «Оплата подписки (payment_claims)» ниже.

## Оплата подписки (payment_claims)

Оплата — ручная (перевод на карту), без интеграции с платёжным провайдером: владелец заведения нажимает «Я оплатил», прикладывает чек, а подтверждает поступление денег человек (суперадмин через `/superadmin/payment-claims` или бот-кнопкой в Telegram). Код при этом уже написан под будущую автоматизацию (Click/Payme) — см. «Провайдер» ниже.

- **Схема** — таблица `payment_claims` (`venue_id`, `months` ∈ {1,3,6,12}, `amount`, `currency`, `method`, `payer_note`, `receipt_url`, `status` ∈ {`pending`,`approved`,`rejected`,`cancelled`}, `reviewed_by`, `reviewed_at`, `reject_reason`, `payment_id` — ссылка на итоговую запись в `payments` после подтверждения). Частичный уникальный индекс `UNIQUE(venue_id) WHERE status='pending'` — у заведения не может быть двух заявок в очереди одновременно; повторная отправка формы, пока первая заявка висит, будет отклонена на уровне БД (в UI это дополнительно блокируется раньше — кнопка отправки скрыта, пока есть `pendingClaim`).
- **Цены и скидки** — `src/config/constants.js`: `PRICE_MONTH_UZS` за месяц, `PERIOD_DISCOUNTS = {1:0, 3:10, 6:15, 12:20}` (скидка в % от периода), `calculatePeriodPrice(months)` считает итоговую сумму с округлением. Меняются в одном месте, если понадобится другая сетка тарифов.
- **Провайдер** (`src/services/payment/`) — `index.js` — фасад с интерфейсом `createInvoice(venueId, months)` / `confirmPayment(claimId, actor)`, выбирающий реализацию по `site_settings.payment_provider` (сейчас всегда `manual`). `providers/manual.js` — единственная реализация: `createInvoice` просто возвращает сумму и реквизиты карты из `site_settings` для показа на экране оплаты; `confirmPayment` — транзакция с `SELECT ... FOR UPDATE` на заявку и заведение, создаёт `payments`, продлевает `subscription_until` (от `max(текущая_дата_окончания, сегодня)`, чтобы досрочная оплата не сжигала уже оплаченные дни), переводит заведение в `active` через `venueLifecycle.reviveToActiveIfNeeded` (это работает и из `archived` — реальная оплата возвращает заведение из архива, поскольку архивация в этой кодовой базе пока не удаляет данные), логирует действие и ставит email-уведомление в очередь. `rejectClaim`/`cancelClaim` живут только в фасаде (не часть интерфейса провайдера — у автоматических провайдеров нет концепции ручной проверки). Все три мутации (`confirmPayment`/`rejectClaim`/`cancelClaim`) идемпотентны: `UPDATE ... WHERE status='pending' RETURNING *` — повторный вызов (двойное нажатие кнопки, гонка бот/веб) возвращает `{ alreadyProcessed: true }` вместо ошибки или повторного списания.
- **Экран владельца** (`/admin/subscription`, `GET /` + `POST /claim` + `POST /cancel-claim`) — если есть `pendingClaim`, показывает карточку ожидания с суммой/датой и кнопкой отмены; иначе — выбор периода (4 карточки с ценой и бейджем скидки, сумма пересчитывается на клиенте при выборе), реквизиты карты (копирование в буфер — тот же паттерн, что и Wi-Fi на публичном меню), комментарий и загрузка чека (необязательны), кнопка отправки. Ниже — история заявок (`payment_claims`, не `payments` — в `payments` нет ни статуса, ни количества месяцев). При отправке заявки уведомление (`payment_claim_created`) улетает в Telegram всем `OWNER_TELEGRAM_IDS` с кнопками «Подтвердить»/«Отклонить» прямо в сообщении.
- **Подтверждение/отклонение** — три равнозначных входа в один и тот же `payment` фасад: веб-форма `/superadmin/payment-claims/:id/confirm|reject`, Telegram-кнопки (`bot/handlers/paymentClaimActions.js`, `claim:confirm:ID` / `claim:reject:ID`) и (для reject) диалоговый ввод причины в боте. Причина отклонения в боте собирается через `bot/lib/pendingRejectReason.js`, обобщённый до `{ type: 'lead' | 'claim', id }` — раньше он помнил только заявки на подключение (лиды), теперь `peekType()` даёт `fallback.js` понять, какой из двух консьюмеров текста должен обработать следующее сообщение оператора, не воруя чужое состояние. Отклонение уведомляет владельца по email (`payment_claim_rejected`) с причиной.
- **Ограничение по чекам** — `src/middlewares/upload.js` (`uploadReceiptPhoto`, до 5 МБ) смонтирован в `app.js` **до** `csrfProtection` на уровне `/admin/subscription` (как и `uploadItemPhoto` для товаров) — Express идёт по порядку регистрации middleware, а multer обязан разобрать `multipart/form-data` раньше, чем CSRF проверит `req.body._csrf`.

## Доступ: пароли, восстановление, привязка Telegram

Всё, что связано со входом в админку венью-админа: выдача первичного пароля, смена, восстановление по почте и через бота, привязка личного Telegram-аккаунта к `admins`, защита `/admin/login` от перебора. Схема — `admins.must_change_password/email/telegram_id/failed_login_count`, `venues.owner_telegram_id`, новые таблицы `password_reset_tokens` и `venue_telegram_links` (5 миграций `178750470000..178750510000`).

- **Первичный пароль** — при одобрении заявки (`leadApproval.approveLead`) и при прямом создании заведения (`POST /superadmin/venues`) новый `admins` создаётся с `must_change_password=true`. Логин и пароль уходят владельцу **двумя отдельными уведомлениями** (`admin_credentials_login` → затем `admin_credentials_password`, `bot/templates/notifications.js`) — та же дешёвая защита от пересылки скриншота, что описана в промте, применена одинаково к Telegram и к email ради единообразия кода. Канал выбирается как и раньше: Telegram заявки, иначе email — оба поля есть в обеих формах создания заведения в суперадминке (`admin_email`, nullable, нужен для восстановления).
- **Принудительная смена** — `src/middlewares/auth.js:redirectIfMustChangePassword` перехватывает любой запрос в контентные разделы админки, пока флаг не снят, и уводит на `/admin/password`. Не middleware внутри роутеров, а отдельные маунты в `app.js` (тот же паттерн, что multer/CSRF-порядок): `/admin/login`, `/admin/logout` и сам `/admin/password` из-под gate’а намеренно выведены, иначе с флагом было бы невозможно даже выйти.
- **`/admin/password`** (`src/routes/adminPassword.js`) — смена пароля (нужен текущий) и привязка Telegram на одной странице, обе секции видны сразу после логина, а не спрятаны по разным местам. Новый пароль: ≥8 символов, не равен логину, не входит в список частых паролей (`src/utils/commonPasswords.js`, ~180 строк, сравнение без регистра) — индикатор надёжности на клиенте (`src/public/js/password-strength.js`) не блокирует отправку, это подсказка. После смены — `src/services/passwordChange.js:applyNewPassword` инвалидирует все ОСТАЛЬНЫЕ сессии этого админа (`DELETE FROM user_sessions WHERE sess->'admin'->>'id' = ...` — `connect-pg-simple` хранит сессии в json-колонке `sess`, отдельной колонки под `admin_id` нет) и шлёт уведомление в оба канала, если оба заполнены.
- **Восстановление по email** (`/admin/forgot` → `/admin/reset`) — ответ формы всегда один и тот же независимо от того, найден аккаунт или нет (анти-энумерация). Токен — 32 случайных байта, в БД только SHA-256 хеш (`src/models/passwordResetTokenModel.js`), TTL 60 минут, одноразовый; создание нового токена сразу гасит предыдущие непогашенные того же админа, а сам обмен токена на новый пароль — атомарный `UPDATE ... WHERE used_at IS NULL AND expires_at > now() RETURNING admin_id` (тот же приём, что и идемпотентные мутации `payment_claims`), что само по себе закрывает гонку двойного использования одной ссылки. Rate-limit — 3/аккаунт/час и 10/IP/час (`src/middlewares/rateLimit.js`), оба лимитера рендерят тот же самый «письмо отправлено» экран, чтобы 429 не стал побочным способом проверить, какие логины существуют. Без привязанной почты `/admin/forgot` не может ничего отправить — статичная (не зависящая от введённого значения) подсказка на странице сразу объясняет это и даёт ссылку на бота.
- **Привязка Telegram** (`src/services/telegramLink.js`, `src/models/venueTelegramLinkModel.js`) — кнопка на `/admin/password` генерирует 6-символьный код без похожих символов (`0/O/1/I`, тот же алфавит-стиль, что у `generatePassword.js`), живёт 15 минут, показывается как код для копирования и как готовая ссылка `t.me/<BOT_USERNAME>?start=link_<code>`. Бот (`bot/handlers/start.js`, `bot.command('start', ...)`) читает payload через `ctx.payload` — **не** `ctx.startPayload`: последний Telegraf проставляет только у специального метода `bot.start(handler)`, а не у обычной регистрации команды, которую использует этот файл. Успешная привязка одной транзакцией устанавливает `admins.telegram_id` и денормализованную копию `venues.owner_telegram_id` (нужна, чтобы `venueLifecycle.notifyVenue` слал напоминания в Telegram без JOIN на `admins`). Повторная привязка того же Telegram-аккаунта к другому `admins` «перетирает» старую: у прежнего владельца снимаются оба поля (включая `owner_telegram_id` его венью, если это другое заведение — иначе там осталась бы устаревшая ссылка), и ему уходит email-уведомление об отвязке. Отвязка из `/admin/password` — с подтверждением (`data-confirm`, `src/public/js/confirm-submit.js`). Бот же даёт «Забыл пароль» (`start:account` → `account:forgot`) — доступно только уже привязанному аккаунту, использует тот же `passwordResetTokenModel`, что и веб-форма, просто без email — ссылка приходит прямо в чат.
- **Защита `/admin/login`** — два независимых рейт-лимитера (`src/middlewares/rateLimit.js`): `loginLimiter` (10/IP/15мин, как и раньше) и новый `loginByAccountLimiter` (5/конкретный логин/15мин, `keyGenerator` по `req.body.login`). Независимо от них `admins.failed_login_count` — персистентный счётчик на аккаунт: с 5 неудачных подряд ответ на каждую следующую попытку намеренно задерживается на 2с (`setTimeout` в обработчике — не блокирует event loop, платит только этот конкретный запрос), на 10 — уведомление владельцу заведения тем же `venueLifecycle.notifyVenue` (шаблон `admin_ten_failed_logins`). Счётчик и задержка считаются только для **существующих** логинов — так не ослабляется уже имеющаяся тайминг-защита от энумерации (`DUMMY_PASSWORD_HASH` в `adminAuth.js`): у несуществующего логина и так нет собственного счётчика, которым можно было бы отличить его от существующего по времени ответа. Каждая неудачная попытка на реальный аккаунт логируется в `admin_action_logs` (`action_type='auth_fail'`, `entity_type='admin'`, хеш IP через общий `src/utils/hashIp.js`, вынесенный из `apply.js`) — видно в `/superadmin/logs`.

## Онбординг: чеклист, пустые состояния, демо-данные (промт 1.6)

Задача — довести нового владельца от пустой админки до опубликованного меню, не давая экрану выглядеть пустым/непонятным на каждом шаге.

- **Чеклист на дашборде** (`src/services/onboarding.js`, `src/models/onboardingModel.js`) — 9 фиксированных пунктов: профиль, контакты, первая категория, 5 позиций, фото у 3 позиций, предпросмотр, публикация, скачивание QR, привязка Telegram. Статус каждого пункта считается из уже загруженного `venue` (профиль/контакты/публикация/QR/предпросмотр) плюс **одним** дополнительным SQL-запросом с агрегатами (`onboardingModel.getChecklistCounts`: категории/позиции/фото/Telegram четырьмя scalar subquery за один round-trip) — не девятью отдельными запросами. «Текущий» пункт (первый невыполненный по фиксированному порядку) — единственный с кнопкой действия; для `publish` это сама форма публикации (недоступна и с пояснением, если `checkPublishReadiness` не пройден), для `qr` — ссылка-скачивание с `download`-атрибутом.
- **Показ/сворачивание** — развёрнуто, пока не всё выполнено, и первые 14 дней после публикации (`venue.published_at`); дальше — тонкая строка с прогрессом, кликабельная для разворота обратно. Сворачивание запоминается кукой `checklist_collapsed_at`, но не булевым флагом, а числом выполненных пунктов НА МОМЕНТ сворачивания: если позже что-то из уже выполненного перестаёт быть выполненным (например, удалили все позиции), текущее число выполненных оказывается меньше сохранённого — и чеклист разворачивается заново автоматически, даже не читая куку как «false» (`onboarding.isCollapsedByCookie`).
- **Демо-данные** (`src/services/demoData.js`) — кнопка «Заполнить примером» в пустом состоянии категорий создаёт 3 категории и 9 позиций (без фото) с флагом `is_demo=true` (`categories`/`items`). Пункт чеклиста «создать категорию» засчитывает демо-категории как есть, а «5 позиций»/«фото у 3-х» и проверка готовности к публикации (`checkPublishReadiness`) — намеренно нет: считают только `is_demo=false`. «Удалить примеры» одним действием сносит и позиции, и категории (в этом порядке — `items.category_id` это `ON DELETE RESTRICT`).
- **Пустые состояния** — `/admin/categories` (нет категорий вообще) и `/admin/items` (каждая категория теперь рендерится отдельно, включая категории без единой позиции — `adminItems.js` больше не строит список из одних только позиций, а идёт от полного списка категорий) получили композицию из иконки/заголовка/объяснения/примера вместо одной строки текста; позиция без фото показывает инлайн-подсказку о требованиях (квадрат, освещение, ≥800px); карточка просмотров на дашборде показывает «данные появятся после первых посещений» вместо графика из одних нулей.
- **Подсказки от бота** (`bot/worker/scheduler.js:checkOnboardingNudges`) — только в Telegram и только если он привязан (`venue.owner_telegram_id`, без фолбэка на email/владельца сервиса, в отличие от остальных уведомлений в этом файле): через 2 дня в `draft` без единой реальной позиции, через 5 дней в `draft` в любом случае, через 3 дня после публикации без скачанного QR — все три через тот же час-в-час планировщик, что и пересчёт статусов подписки, с `dedup_key` на заведение (не повторяются) и проверкой условия в момент отправки, а не в момент планирования. Планировщик ради этого стал забирать и `draft`-заведения тоже — раньше `venueModel.listForLifecycleRecalc()` исключал их как не нуждающиеся в пересчёте статуса, что для самого пересчёта всё ещё верно, а для этих подсказок нет.

## Модификаторы: размеры и добавки (промт 2.1)

У позиции может быть до 5 групп выбора (`item_option_groups`), в каждой до 20 вариантов (`item_options`): размер, сироп, соус. Позиция без групп ведёт себя ровно как раньше — «+» кладёт её в корзину сразу.

- **Схема** — `item_option_groups` (`item_id` CASCADE, названия ru/uz/en, `selection` ∈ {`single`,`multiple`}, `is_required`, `min_select`, `max_select`, `sort_order`) и `item_options` (`group_id` CASCADE, названия, `price_delta`, `is_available`, `is_default`, `sort_order`). CHECK'и в БД: `min_select >= 0`, `max_select >= min_select`, для `single` — `max_select = 1` и `min_select <= 1`, `price_delta >= 0` (только надбавка: скидка легко увела бы цену в минус; «маленькая порция дешевле» решается тем, что маленькая делается базовой ценой). Лимиты 5/20 живут в валидаторе (`src/validators/itemOptionValidators.js`), а не только в БД — из констрейнта пользователь получил бы нечитаемый текст.
- **Где редактируется** — внутри модалки редактирования позиции (`src/views/partials/item-option-groups.ejs`), но **не** в форме создания: у несохранённой позиции ещё нет `item_id`, и группы некуда привязать. Новая позиция создаётся как раньше, группы добавляются при следующем открытии её на редактирование. Формы групп/вариантов лежат соседними блоками ПОСЛЕ формы позиции — вложенные `<form>` невалидны.
- **Порядок вариантов** — перетаскиванием (`src/public/js/option-reorder.js`, нативный HTML5 drag&drop, без библиотек; новый порядок уходит одним JSON-запросом на `/admin/item-options/groups/:id/reorder`) и продублирован кнопками «вверх/вниз» обычными формами — на тач-устройствах и без JS порядок всё равно меняется.
- **Копирование** — «применить группу к другим позициям» и «скопировать группу из другой позиции» это одно и то же действие с разных сторон (`POST /admin/item-options/groups/copy`: источник + список целевых позиций), клонируется группа вместе с вариантами. Целевые позиции проверяются на принадлежность заведению, у кого уже 5 групп — молча пропускаются.
- **В строке меню** — подпись-счётчик вида «Размер: 3 · Сироп: 2» (название группы + число доступных вариантов). Промт предлагал «2 размера · 3 добавки», но в ru/uz/en у произвольного названия группы нет способа согласовать число («3 размера», но «3 сиропа»), а название + счётчик грамматично на всех трёх языках и вдобавок говорит, ЧТО можно выбрать. Если хоть у одного доступного варианта есть надбавка, цена показывается как «от N».
- **Модалка выбора** (`#item-options-modal`, одна на всё меню — содержимое рисует `src/public/js/menu-cart.js` по данным из JSON-блока `#menuData`; отдельный `<dialog>` на каждую позицию раздул бы страницу). Нативный `<dialog>` + нативные `radio`/`checkbox` — фокус-ловушка, Escape и клавиатурная навигация достаются бесплатно, кастомизация только через CSS. Итоговая цена пересчитывается на лету и стоит прямо на кнопке; кнопка заблокирована, пока не выбрано необходимое; при достижении `max_select` остальные чекбоксы группы блокируются с подсказкой, а не молча игнорируют клик. На мобильном — шторка снизу (`.modal-sheet`), закрывается свайпом вниз, кликом по затемнению и Escape.
- **Корзина** — ключ строки: id позиции без опций (как раньше) либо `id:отсортированные-option_id` с опциями, поэтому один и тот же кофе с разными наборами — разные строки. Под названием мелким шрифтом перечислены выбранные опции, «Изменить» открывает ту же модалку с предзаполненным выбором (смена набора переносит количество на новый ключ). При каждой загрузке страницы корзина сверяется с актуальным меню: исчезнувшие и ставшие недоступными опции убираются, цена пересчитывается по текущей, при потере опций показывается ненавязчивое уведомление. Суммы считаются на клиенте только для отображения — при появлении настоящего заказа (промт 2.4) их придётся пересчитать на сервере.
- **Недоступность** — вариант с `is_available=false` виден приглушённым и не выбирается; если в обязательной группе (или группе с `min_select > 0`) не осталось ни одного доступного варианта, позиция целиком показывается недоступной: выбрать нечего, а без выбора добавить нельзя.

## Карточка блюда и расширенные данные о позиции (промт 2.2)

- **Схема** — на `items` добавлены `weight_value numeric(8,2)` + `weight_unit` (CHECK `g`/`ml`/`pcs`, оба нужны вместе или оба `NULL` — проверяется и в валидаторе, и связкой CHECK'ов в БД), `cooking_time_minutes`, `allergens text[]` (CHECK на 12 допустимых кодов, `NOT NULL DEFAULT '{}'`), `spicy_level smallint` (0..3), `is_popular boolean DEFAULT false`. Бинарный тег `spicy` в `tags` оставлен ради обратной совместимости с уже отфильтрованными по нему меню; миграция разово переносит данные (`spicy_level = 1 WHERE 'spicy' = ANY(tags)`), дальше это два независимых поля — тег продолжает участвовать в фильтре меню, `spicy_level` определяет иконки перца. CHECK на `items.tags` расширен `lactose_free`/`gluten_free`/`chef_choice`.
- **Админка** — поля веса/времени/аллергенов/остроты сгруппированы в сворачиваемый `<details class="extra-fields">` «Дополнительно» (`src/views/partials/item-form-fields.ejs`), доступны и в форме создания, и в форме редактирования (в отличие от групп опций 2.1, у которых есть предусловие «нужен `item_id`» — здесь его нет). Аллергены — чекбоксы с названиями (`src/i18n/*.json → allergens.*`), не кодами. Острота — `.segmented` из 4 радиокнопок, подпись каждой ненулевой — повторяющиеся 🌶 (уровень 2 = 🌶🌶), а не число, считывается быстрее на маленьком экране.
- **Публичная карточка блюда** — одна общая модалка на всё меню, `#dish-card-modal` (`src/views/public/menu.ejs`) + `src/public/js/dish-card.js`, тем же приёмом, что и модалка опций из 2.1: статичная разметка, контент рисует JS по данным из `#menuData`. Блок выбора опций внутри карточки — не вторая реализация, а переиспользование: `menu-cart.js` выставляет `window.menuCart` (рендер групп, пересчёт валидности/цены, добавление в корзину), `dish-card.js` дёргает те же функции. Порядок загрузки в `menu.ejs` важен: `menu-cart.js` — раньше `dish-card.js`.
- **Открытие** — тап по всей строке (не только «+»): название рендерится настоящей `<button data-dish-open>` с растянутым `::after` на всю `.dish-row`, а не `onclick` на `<div>` — доступное имя и клавиатурная активация достаются бесплатно. Блок цены/«+»/степпера лежит поверх по `z-index`, у него по-прежнему свой обработчик (открывает быструю модалку опций или сразу кладёт в корзину, карточку не трогает); `.dish-price` дополнительно `pointer-events: none`, чтобы клик по самой цене не проваливался мимо растянутой кнопки.
- **URL и история** — открытие карточки зовёт `history.pushState` (`?item=<id>`), кнопка «назад» браузера закрывает карточку через `popstate`, а не уходит со страницы. Переход по ленте «ещё из этой категории» из уже открытой карточки в другую делает `replaceState`, а не второй `pushState` — иначе цепочка из нескольких открытых подряд карточек потребовала бы кучу нажатий «назад», чтобы просто закрыть последнюю. Закрытие идёт через один-единственный путь — функцию `closeCard()`, которую дёргают и кнопка/свайп/добавление в корзину, и событие `close` нативного `<dialog>` (Escape, клик по затемнению из `modal.js`) — так возврат скролла и снятие записи истории гарантированно происходят один раз, из какой бы точки карточку ни закрыли.
- **Прямая ссылка** (`/menu/:slug?item=<id>`) — сервер (`buildFullViewModel` + `itemLinkExtras` в `src/routes/publicMenu.js`) рендерит карточку сразу открытой (через `#menuData.initialItemId`) и подменяет мета-теги (title/description/og:*) на теги позиции, а не заведения — так ссылка на конкретное блюдо разворачивается своим превью в Telegram/Instagram, а не общей карточкой меню. Раз мета-теги завязаны на конкретную позицию, такой запрос **не** обслуживается из общего `menuCache` (он кэшируется по `slug:lang`, без учёта `item`) — идёт мимо кэша каждый раз, как и предпросмотр черновика владельцем.
- **Блокировка скролла фона** — `position: fixed` на `<body>` с сохранением и восстановлением `scrollY` (класс `.scroll-locked`); только `position: fixed`, а не `overflow: hidden`, держит и iOS Safari. Прокручивается только тело карточки, шапка с фото и подвал с кнопкой добавления не сжимаются (`max-height` на диалоге + `flex`), поэтому даже у очень длинного описания кнопка остаётся закреплённой снизу.
- **Фото** — прогрессивная загрузка: снизу уже загруженное превью из строки меню (растянутое, `blur(14px)`), поверх полноразмерная версия, которая проявляется по `load`/`error`. Если фото нет вовсе — не пустое место, а заглушка с иконкой `utensils` на фоне `--background`.
- **Edge cases** — позиции по прямой ссылке больше нет или её сняли с продажи: карточка всё равно открывается (не 404), с пометкой «этой позиции больше нет в меню» и кнопкой возврата, без фото и без блока выбора опций/цены; на мобильном высота диалога в этом состоянии не на весь экран, а под контент (класс `.is-gone`). Suspended/is_active=false заведение с `?item=` — обычная страница-заглушка заведения, как и без параметра, карточка не рендерится вовсе (ветка `renderUnavailable` отрабатывает раньше, чем читается `item`). Открытие/закрытие карточки не трогает состояние поиска и фильтров на фоне — они живут в DOM строк меню, который карточка не перерисовывает.
- Ловушка CSS, всплывшая на этой карточке: закрытый `<dialog>` браузер сам прячет UA-стилем `dialog:not([open]) { display: none }`, но любой наш `display: flex` на том же селекторе (понадобился `.dish-card`, чтобы шапка/тело/подвал не сжимались) перебивает это правило — авторские стили всегда сильнее браузерных. Без явного `dialog.modal:not([open]) { display: none }` в `design-system.css` закрытая модалка-шторка осталась бы в DOM и перехватывала клики поверх страницы.

## Печатные QR-макеты в PDF (промт 3.4)

- **Зависимость** — `pdfkit`, без headless-браузеров. Шрифты: вариативные TTF Manrope и Playfair Display в `src/public/fonts/print/` (OFL, из официального репозитория `google/fonts`, лицензия рядом в `OFL.txt`). Отдельные файлы понадобились потому, что вебу отдаются woff2, а pdfkit их не читает; вариативный TTF содержит все начертания в одном файле, поэтому их всего два.
- **Дыры в глифах, найденные проверкой шрифтов** (`src/services/print/text.js`): в Manrope нет `ʻ` (U+02BB — апостроф узбекской латиницы: `oʻzbekcha`) и `Қ Ғ Ҳ`, в Playfair нет `Ҳ ҳ` и `₽`. Русская кириллица, латиница и диакритика есть в обоих. Поэтому весь текст перед отрисовкой проходит нормализацию (типографские апострофы и кавычки → те, что в шрифте есть) и подстановку близких глифов; админка отдельно предупреждает, какие символы названия будут заменены. Без этого в PDF оказался бы пустой прямоугольник `.notdef`.
- **QR — вектор, но не из SVG.** Библиотека `qrcode` рисует код горизонтальными штрихами через `stroke`, и парсить такой путь ради pdfkit хрупко. Берётся матрица модулей (`QRCode.create`) и каждый тёмный модуль рисуется прямоугольником — тот же вектор, но без посредника, и одинаково работает в обоих бэкендах.
- **Один макет — два «принтера».** `src/services/print/canvas.js` задаёт интерфейс рисования (в миллиметрах), а реализации две: pdfkit для скачивания и SVG для предпросмотра. Это способ выполнить требование промта «предпросмотр рендерится ТЕМ ЖЕ кодом», не имея растеризатора PDF (в системе нет ни pdftoppm, ни mupdf) и не заводя headless-браузер, который промт прямо запрещает. Замеры текста в обоих бэкендах делает fontkit, поэтому переносы, автоподбор кегля и координаты совпадают до миллиметра — предпросмотр не может разъехаться с PDF.
- **Печатные правила зашиты в код, а не в инструкцию.** `planQr` считает геометрию и **бросает** `QR_TOO_SMALL`, если физический размер кода получается меньше 25 мм: настройки не могут сделать нечитаемый QR. Тихая зона — ровно 4 модуля во всех макетах. Фактические размеры кодов: 30.6 мм (визитка) … 88.5 мм (лист A4). Код всегда тёмный на светлом: при заливном фирменном фоне он лежит на светлой карточке, а не выворачивается.
- **Шесть макетов**: тейбл-тент (лист A5 со сгибом посередине, верхняя половина развёрнута на 180° — сложенный даёт стоящую «палатку» A6, читаемую с обеих сторон), круглая наклейка 80 мм с контуром вырубки, наклейка-визитка 90×50, лист A4 на стену, лист A4 с 12 одинаковыми наклейками под резку и лист A4 «QR по столам» с номерами. Первые четыре идут с вылетами 3 мм и метками реза, листы-сетки — с метками реза на полях.
- **Экран `/admin/print`** — карточки макетов, языки призыва (два языка = две строки), тумблеры логотипа и контактов, диапазон столов, предпросмотр в модалке и скачивание. Технические подписи: размер в мм, «печатать 100%, без масштабирования», плотность бумаги, наличие вылетов.
- **Домен сервиса внизу макетов** — `site_settings.print_domain`, редактируется суперадмином в «Настройки сайта → Печатные материалы». Лежит именно там, а не в `venues` и не в `.env`: это наш адрес, один на весь сервис (рядом с `owner_name` и `offer_url`), и менять его нужно из интерфейса, без правки конфига и перезапуска. Вводится так, как должен быть напечатан (`menuva.uz`); схема и хвостовые слэши срезаются валидатором, так что вставленное из адресной строки `https://menuva.uz/` тоже подойдёт. Пока поле пустое, блок не рисуется вообще и НЕ резервирует место — незанятая строка внизу выглядела бы как дефект вёрстки. На листах-сетках домен печатается в каждой ячейке (по одному на изделие).
- **Логотип** берётся только из локальных `/uploads` и перегоняется в PNG через уже имеющийся sharp (pdfkit не понимает webp, в котором лежат загруженные логотипы). Внешние http-ссылки из демо-данных намеренно игнорируются: ходить с сервера по произвольному URL из базы ради картинки не нужно. Без логотипа макет перестраивается без пустого места.
- **Edge cases.** Длинное название: сначала уменьшается кегль, потом перенос на две строки, потом обрезка многоточием — причём ширина проверяется у КАЖДОЙ строки, иначе одно длинное слово без пробелов («Рестораннаберезинойулице») возвращалось бы единственной строкой любой ширины и уезжало за край. Slug и токен экранируются через `URLSearchParams`. Генерация потоковая (пишется прямо в ответ), предел 200 страниц, 250 столов рендерятся за ~0.7 с. Заведению в статусе draft печатать можно, но экран предупреждает, что QR у гостя пока не откроется.
- **Чего я не проверял:** сканирование напечатанных макетов реальным телефоном. Промт требует этой проверки, и в самом файле промтов она же вынесена в раздел «что делаешь руками». Программно гарантированы размер, тихая зона, контраст и корректность ссылки в коде — физическую читаемость на дешёвой камере нужно подтвердить вручную.

## Столы, заказы и вызов официанта (промт 2.4)

- **Схема** — `venue_tables` (номер текстом: бывают «Терраса 3»; `token` из 8 случайных символов и UNIQUE), `venue_telegram_group_links` (коды привязки группы), `orders` + `order_items`, `waiter_calls`, плюс на `venues`: `telegram_chat_id/title/linked_at/broken`, `orders_enabled`, `min_order_amount`.
- **Почему токен, а не `?table=7`** — с предсказуемым номером любой прохожий вызвал бы официанта к любому столу. Перевыпуск токена (кнопка в админке) мгновенно убивает старый QR. Ссылка в QR — `/menu/:slug?t=<token>&src=qr` (метка источника из промта 3.2 переиспользована).
- **Стол не попадает в HTML меню.** Страница кэшируется по `slug:lang`, поэтому вкладка гостя за столом 5 раздавала бы «стол 5» всем остальным. Токен резолвится в httpOnly-cookie на 3 часа (`mt_<slug>`), а экран заказа спрашивает актуальный стол отдельным запросом `GET /order/:slug/context` (без кэша). При самой отправке сервер перерезолвит стол из той же cookie — клиент не может назначить себе стол сам.
- **«Скачать все QR»** — страница `/admin/tables/print` с сеткой кодов и печатью браузера (в том числе «сохранить как PDF»). Отдельной библиотеки для ZIP/PDF ради одной кнопки не заводили.
- **Привязка группы** — своя таблица, а не `venue_telegram_links` из промта 1.5: там привязывается ЛИЧНЫЙ аккаунт админа через deep-link `/start`, здесь — групповой чат, и код гасится сообщением в самой группе (`bot/handlers/telegramGroupLink.js`). Одна группа обслуживает одно заведение (иначе обратный поиск «чей это чат» стал бы неоднозначным). Подтверждение бота в группе и есть требуемое промтом «тестовое сообщение»: если отправить его не удалось, связь сразу помечается разорванной.
- **Сопутствующая правка `bot/handlers/fallback.js`** — он отвечал «не понимаю» и пересылал владельцу сервиса ЛЮБОЕ текстовое сообщение. После появления привязанных групп (бот там администратор, режим приватности не действует) это означало бы ответ на каждую реплику персонала. Теперь catch-all работает только в личке.
- **Как заказ доходит до группы.** Веб и бот — разные процессы, живого Telegraf-инстанса в вебе нет, поэтому заказ кладётся в существующий аутбокс `notifications`, а воркер бота его отправляет. Воркер при этом впервые **записывает `message_id` результата обратно** в `orders`/`waiter_calls` — без него кнопкам «Принят»/«Готово»/«Иду» нечего было бы редактировать. Обратная сторона: аутбокс опрашивается раз в 10 секунд, значит между отправкой заказа и сообщением в группе может пройти до 10с — как у заявок и оплат, которые ходят через тот же аутбокс.
- **Кнопки статуса** обрабатывает сам процесс бота (`bot/handlers/orderActions.js`) и редактирует ИСХОДНОЕ сообщение, а не шлёт новое. Идемпотентность — условием на текущий статус прямо в `UPDATE ... WHERE status = 'new' RETURNING *`: второй нажавший получает «уже обработано», а не второе редактирование. Отдельной проверки «кто нажал» нет и не нужно: кнопка живёт только на сообщении внутри привязанной группы. Сверяется лишь то, что чат нажатия принадлежит заведению заказа.
- **Пересчёт на сервере** (`src/services/orderPricing.js`) — из присланного клиентом берутся ТОЛЬКО идентификаторы и количества, названия и цены читаются из БД. Клиент не может ни занизить цену, ни заказать позицию чужого заведения, ни подсунуть опцию от другого блюда. Расхождение суммы, исчезнувшая позиция, кончившаяся опция и несоблюдённые лимиты обязательных групп — всё это возвращается гостю списком проблем, заказ не уходит.
- **Часы работы** — `src/utils/workingHours.js`, вынесенная как есть эвристика клиентского бейджа «открыто сейчас» (первый интервал `ЧЧ:ММ–ЧЧ:ММ` из свободного текста `venues.working_hours`, действует каждый день). Так сервер и бейдж не расходятся: гость, видящий «открыто», обязан иметь возможность заказать. Унаследованное ограничение — разные часы по дням недели не разбираются; строгий разбор потребовал бы структурированного расписания вместо свободного текста, это отдельная задача.
- **Антиспам** — 3 заказа и 10 вызовов на `session_hash` в час (считается по БД, чтобы переживать рестарт) плюс 30 заказов на IP в час (`express-rate-limit`). Кулдаун вызова официанта — 2 минуты на СТОЛ, тоже по БД: двое за одним столом не должны звать дважды подряд.
- **Edge cases.** Бот удалён из группы в момент отправки: заказ остаётся в БД, связь помечается разорванной, владелец получает алерт (через ту же цепочку `notifyVenue`: личный Telegram → email → владельцу сервиса), а гость на экране статуса видит `delivered: false` и подсказку «покажите заказ официанту» — отправка асинхронная, поэтому узнать об этом можно только там. Группа переехала в супергруппу — `migrate_to_chat_id` из ошибки обновляет `chat_id` автоматически, запись уходит в короткий ретрай. Токен стола деактивирован/перевыпущен — заказ обрабатывается как «без стола», с просьбой ввести номер.

## Бэкапы и восстановление (промт 4.1)

- **Скрипты, а не node-cron** (прямое требование промта): `scripts/backup.sh` под systemd-таймером. Бэкап не должен зависеть от того, жив ли Node-процесс, — ровно те ночи, когда приложение упало, для бэкапа самые важные. Общее для всех трёх скриптов (конфигурация, лог, алерты, файл состояния, место на диске) вынесено в `scripts/backup-lib.sh`, чтобы у них не разъехались ни имена переменных, ни формат состояния.
- **Порядок операций продиктован edge cases промта и соблюдается буквально:** дамп базы → снимок uploads → манифест → вторая копия → и ТОЛЬКО ПОТОМ удаление старых. uploads снимаются ПОСЛЕ дампа: файлы, добавленные между шагами, попадут в следующий инкремент, и это нормально — важно не терять старые. Обратный порядок ротации («сначала освободить место, потом писать») означал бы, что неудачная ночь оставляет и без нового бэкапа, и без старых; проверка на это есть отдельная.
- **Инкремент uploads — `rsync --link-dest`, а не `tar --listed-incremental`.** Промт разрешает оба, разница в том, как они ломаются: порванная цепочка tar-инкрементов теряет всё, что после неё, а битый rsync-снимок теряет только себя. Плюс каждый снимок — просматриваемое дерево целиком (неизменившиеся файлы в нём жёсткие ссылки на вчерашние и места не занимают), и восстановление фото сводится к обычному копированию вместо проигрывания цепочки.
- **Манифест** рядом с каждым дампом: дата, размер, sha256, версия схемы (последняя применённая миграция), число заведений и позиций, число файлов в uploads — и версия PostgreSQL. Последнюю промт требует зафиксировать отдельно: восстановление на более старый мажор не работает, и узнать об этом лучше заранее, чем во время аварии. Счётчики не украшение: пустая база даёт совершенно валидный дамп, который иначе заметят только при попытке восстановиться, поэтому ноль заведений считается аварией и бэкап падает.
- **Алерты — напрямую в Telegram Bot API из bash**, как во внешнем мониторе (промт 4.2), а не через очередь уведомлений приложения. Бэкап обязан достучаться именно тогда, когда приложение или база лежат, — а очереди нужны оба. Успешный бэкап не пишет НИЧЕГО (промт: «иначе владелец перестанет их читать»); неудачный шлёт алерт сразу, вторая неудача подряд — с пометкой критичности (счётчик живёт в файле, между запусками процесса общей памяти нет).
- **Файл состояния — тот же, что читает `/health/detailed`.** Контракт задан ещё промтом 4.2 (`lastBackup()` в `src/routes/health.js` читает `lastSuccessAt` и `lastStatus`); скрипт пишет ровно эту форму плюс поля, которые health-check игнорирует, но которые полезны человеку: `consecutiveFailures`, `lastVerifyAt`, `lastError`. Пишется атомарно через временный файл и `mv` — health-check читает его в произвольный момент и застать наполовину записанный JSON не должен. `BACKUP_STATE_FILE` в `scripts/backup.env` обязан совпадать с одноимённой переменной в `.env` приложения.
- **Восстановление по умолчанию НЕ в продакшен.** `scripts/restore.sh` без аргументов накатывает последний дамп в `<база>_restore_test`. Боевая база требует трёх барьеров подряд: точного совпадения имени, флага `--i-mean-it` и ввода имени базы с клавиатуры. Цена ошибки здесь не «перезапустить скрипт», а «потеряли данные, которые как раз и восстанавливали». Контрольная сумма сверяется ДО наката: битый файл лучше обнаружить сейчас, чем на середине. Расхождение мажорной версии PostgreSQL печатается предупреждением в момент действия — README посреди аварии никто читать не станет.
- **Еженедельная проверка восстановления** (`scripts/verify-backup.sh`) поднимает последний дамп в одноразовую базу ЧЕРЕЗ ТОТ ЖЕ `restore.sh`, которым будут пользоваться в аварии (проверять свою отдельную реализацию значило бы подтверждать работоспособность чего-то другого), сверяет счётчики с манифестом, проверяет целостность внешних ключей явными запросами на осиротевшие строки, удаляет тестовую базу и шлёт единственную регулярную сводку: размер базы и фото с динамикой за неделю, размер последнего дампа, число хранимых копий, свободное место и дату последней успешной проверки. Непроверенный бэкап — не бэкап.
- **Что проверено эмпирически.** `npm run check:backup` (50 проверок) прогоняет НАСТОЯЩИЙ `backup.sh` в песочнице с заглушками вместо `pg_dump`/`psql`: обрыв дампа, зависший pg_dump с таймаутом, обрезанный дамп, пустая база, пороги места (15% — предупреждение и бэкап идёт, 5% — отказ и ничего не трогается), ротация 7/4/6 с проверкой, что удалены ровно самые старые, неудаление старых при провале нового, вторая копия и её недоступность, инкремент uploads с жёсткими ссылками и историей удалённых файлов. На Windows шаг с uploads и второй копией честно пропускается (в Git Bash нет rsync) и об этом печатается предупреждение — полный прогон делается на Linux: `docker run --rm -v "$PWD:/app" -w /app alpine:3 sh -c 'apk add --no-cache bash rsync coreutils findutils gawk && bash scripts/check-backup.sh'`.
- **Настоящий цикл пройден руками** (DoD промта): дамп боевой базы через `backup.sh` → 153 КБ, манифест с 5 заведениями, 90 позициями, схемой `1787508600000` и PostgreSQL 16.15 → `restore.sh` в `qrmenu_restore_test` → 5 заведений и 90 позиций на месте, боевая база не тронута → `verify-backup.sh` с контрольными запросами и удалением тестовой базы. Отдельно проверено, что порченый дамп отбивается по контрольной сумме, а восстановление в продакшен без `--i-mean-it` отказывает.
- **Чего проверить было нечем:** таймеры systemd, копирование по ssh на другой сервер (проверено копирование в локальный каталог — тот же код rsync, только без сети) и само расписание 04:00 по Ташкенту. Тот же честный остаток, что с certbot в промте 3.7.

### Установка

```bash
cp scripts/backup.env.example scripts/backup.env
chmod 600 scripts/backup.env          # там пароль к базе и токен бота
$EDITOR scripts/backup.env
mkdir -p /var/backups/qrmenu /var/lib/qrmenu
bash scripts/backup.sh --dry-run      # показывает, что будет сделано, ничего не меняя
```

`BACKUP_DIR` обязан быть на ДРУГОМ физическом диске, чем база. Бэкап на том же диске, что и БД,
бэкапом не является — он умрёт вместе с ней.

**Таймеры systemd** (время в юните — по часовому поясу сервера; для 04:00 по Ташкенту сервер
должен быть в `Asia/Tashkent` либо используйте `OnCalendar=*-*-* 23:00:00 UTC`):

```ini
# /etc/systemd/system/qrmenu-backup.service   (Type=oneshot, User=root)
ExecStart=/opt/qrmenu/scripts/backup.sh

# /etc/systemd/system/qrmenu-backup.timer
OnCalendar=*-*-* 04:00:00
Persistent=true          # пропущенный из-за выключенного сервера бэкап догонится при старте

# /etc/systemd/system/qrmenu-backup-verify.timer
OnCalendar=Mon *-*-* 05:00:00
Persistent=true
```

`Persistent=true` важен: без него сервер, выключенный в 04:00, просто пропустит ночь молча.

### Восстановление на чистом сервере

Порядок обязателен: база → фото → миграции → запуск. Обратный порядок даёт приложение,
поднявшееся на пустой базе и успевшее что-то в неё записать.

```bash
# 0. Поставить те же версии: PostgreSQL — мажор из манифеста (поле postgresVersion),
#    Node 20. Восстановление на БОЛЕЕ СТАРЫЙ мажор PostgreSQL не работает.
cat /var/backups/qrmenu/daily/qrmenu-*.manifest.json | tail -20

# 1. Код и зависимости.
git clone <репозиторий> /opt/qrmenu && cd /opt/qrmenu && npm ci --omit=dev

# 2. .env — ИЗ ОТДЕЛЬНОГО ЗАШИФРОВАННОГО ХРАНИЛИЩА, его в общем бэкапе нет и быть не должно.
#    SESSION_SECRET обязан совпадать со старым, иначе все сессии и хеши аналитики станут
#    недействительными.
cp /secure/qrmenu.env .env && chmod 600 .env

# 3. База. Сначала создать пустую, потом накатить дамп.
createdb -U qrmenu qrmenu
./scripts/restore.sh --file /var/backups/qrmenu/daily/qrmenu-ГГГГММДД-ЧЧММСС.dump \
                     --into qrmenu --i-mean-it

# 4. Фото.
./scripts/restore.sh --uploads-only --snapshot ГГГГ-ММ-ДД

# 5. Миграции: дамп содержит схему на момент бэкапа, а код мог уйти вперёд.
npm run migrate:up

# 6. Запуск и проверка.
npm start
curl -s localhost:3000/health
curl -s -H "X-Health-Token: ..." localhost:3000/health/detailed | jq .
```

## Мониторинг, алерты и безопасность (промт 4.2)

### Health-check

- `GET /health` — намеренно остался простым и быстрым (`{status, db}`): его дёргает внешний монитор каждые две минуты.
- `GET /health/detailed` (`src/routes/health.js`) — подробный отчёт: подключение к БД и задержка, счётчики пула (`total`/`idle`/`waiting` — последнее и есть ранний признак, что пул стал узким местом), свободное место на диске, размер каталога uploads, uptime, память, последняя применённая миграция, статус LISTEN-соединения, размер очереди `notifications`, число pending `payment_claims`, время последнего бэкапа, права на `.env` и `uploads`. Ответ 200, если всё в норме; **503 со списком проблем** при деградации.
- Доступ: **только с localhost или по `HEALTH_TOKEN`**. Постороннему отвечает **404, а не 403** — наличие подробного health-check это тоже сведения. Токен сравнивается в постоянное время.
- Размер uploads кэшируется на минуту: обход тысяч файлов на каждый запрос недопустим, а меняется он медленно.
- **Бэкапы.** Промт 4.1 ещё не сделан, механизма нет. Отчёт читает необязательный `BACKUP_STATE_FILE` и, если он не задан, честно пишет «бэкапы не настроены» — и это сразу переводит статус в `degraded`. Рисовать зелёный статус для бэкапов, которых не существует, — худшее, что можно сделать в мониторинге.
- Права на файлы на Windows не проверяются (`checked: false, reason: windows`) — режимы POSIX там не имеют смысла, и показывать по ним «всё в порядке» было бы враньём.

### Внешний монитор

`scripts/monitor.sh` — **запускать с другой машины**, cron раз в 2 минуты (`scripts/monitor.env.example` — конфигурация). Монитор на том же сервере ляжет вместе с ним. Проверки: `/health`, время ответа публичного меню, срок сертификата, `getMe` бота, подробный health по токену. Алерты уходят **напрямую в Telegram Bot API через curl**, не через приложение — в этом весь смысл: он должен работать, когда приложение не работает.

Пороги — из промта: недоступность дольше 3 минут, ответ медленнее 3 секунд подряд 5 раз, сертификат за 14 дней. Состояние между запусками лежит в `MONITOR_STATE_DIR`, поэтому повторные алерты не дублируются, а восстановление уведомляется отдельно: «сервис снова доступен, простой составил N минут». Проверено вживую: алерт при простое 5 минут пришёл один раз, повторный запуск его не продублировал, после подъёма сервиса пришло сообщение о восстановлении.

### Ошибки приложения

- Централизованный обработчик в `src/app.js` дополнен алертом владельцу сервиса и структурированной записью в лог. Наружу по-прежнему уходит только страница `errors/500` — ни стека, ни текста ошибки.
- **Дедупликация обязательна и реализована** (`src/services/errorAlerts.js`): один и тот же стек — не чаще раза в 15 минут, в следующем алерте счётчик повторов («×137» говорит о проблеме больше, чем 137 одинаковых сообщений). Отпечаток считается по стеку И маршруту, а не по тексту: одна и та же строка «Cannot read properties of undefined» из разных мест кода — разные проблемы.
- **Фильтр чувствительных ключей** — рекурсивный, по подстроке в нижнем регистре (`password`, `token`, `csrf`, `cookie`, `authorization`, `session`, `card`, …), с ограничением глубины и защитой от циклических ссылок. В алерт попадают маршрут, id заведения, роль, первые 6 строк стека и очищенное тело запроса.
- Проверка — `npm run check:error-alerts`: 22 утверждения, включая «50 одинаковых ошибок дали не больше одного алерта» и «две разные ошибки дали два» (дедупликация не должна превращаться в «первая ошибка заглушила все остальные»). Отдельно проверено сквозным прогоном на живой 500-ке: 5 запросов на падающий маршрут дали 1 алерт, а гость увидел только «Что-то пошло не так» без стека и текста ошибки.
- **В поле `route` попадает только путь, без query-строки.** Сквозная проверка поймала утечку: фильтр чистит разобранный `req.query`, а `req.originalUrl` несёт сырую строку целиком, и секрет, переданный параметром адреса (`?password=…`), уезжал в алерт мимо фильтра. Параметры отправляются отдельным полем, уже очищенным.
- **Логи** — `src/services/logger.js`: одна строка JSON на запись, ротация по размеру (10 МБ × 5 файлов), синхронная запись (асинхронная очередь теряет последние строки ровно тогда, когда они нужнее всего — при падении). stdout остаётся человекочитаемым. Каталог по умолчанию `./logs`, он в `.gitignore`.

### Что делать, если

**Сервис не отвечает**

```bash
systemctl status qrmenu            # или: pm2 status
journalctl -u qrmenu -n 200 --no-pager
tail -n 200 /path/to/logs/app.log
systemctl restart qrmenu
curl -s localhost:3000/health
```

Если после перезапуска падает снова — смотреть последние строки `app.log` с `"level":"error"`: там уже лежит структурированная запись с маршрутом и стеком.

**БД не поднимается**

```bash
docker compose ps
docker compose logs db --tail 100
df -h                              # Postgres не стартует при заполненном диске
docker compose up -d db
psql "$DATABASE_URL" -c 'SELECT 1'
```

**Диск заполнен**

```bash
df -h
du -sh /path/to/public/uploads /path/to/logs /var/lib/docker
rm -f /path/to/logs/app.log.[3-5]  # ротация оставляет 5 файлов по 10 МБ
docker system prune -f             # неиспользуемые образы и слои
```

Затем разобраться с настоящей причиной: `/health/detailed` показывает размер `uploads` и число файлов.

**Бот молчит**

```bash
systemctl status qrmenu-bot
curl -s "https://api.telegram.org/bot<TOKEN>/getMe"
psql "$DATABASE_URL" -c "SELECT status, count(*) FROM notifications GROUP BY status"
```

Растущий `pending` при живом API означает, что стоит именно процесс бота, а не Telegram. `failed` с `last_error` — смотреть текст ошибки в той же таблице.

**Сертификат истёк**

```bash
certbot certificates
certbot renew --dry-run
certbot renew && systemctl reload nginx
```

Монитор предупреждает за 14 дней; если предупреждения не было — проверить, что `monitor.sh` вообще запускается (`grep monitor /var/log/syslog`).

**Пришёл алерт о неудачном бэкапе**

```bash
cat "$BACKUP_STATE_FILE"           # что именно упало и когда был последний успех
ls -lh /path/to/backups | tail
df -h
```

Не восстанавливать поверх рабочей БД, не проверив дамп: сначала поднять копию на отдельной базе и убедиться, что данные на месте.

## PWA и офлайн (промт 2.5)

- **Манифест на заведение** — `GET /menu/:slug/manifest.webmanifest` (`src/routes/publicPwa.js`), кэшируется и сбрасывается вместе с меню (`menuCache.setManifest`/`invalidate`). Роутер смонтирован на `/menu` РАНЬШЕ `publicMenuRoutes`: там есть `/:slug/:categoryId`, который иначе принял бы `manifest.webmanifest` за id категории. `scope` — `/menu/:slug`, поэтому ссылка на лендинг или чужое меню открывается в обычном браузере, а не внутри «приложения заведения». `theme_color`/`background_color` — литералы `#c65d42`/`#f8f7f3`: это те же токены `--primary`/`--background`, но в манифесте переменные не работают, и менять их надо парой.
- **Иконки** генерируются из логотипа через sharp ПРИ ЗАГРУЗКЕ (`photoService.saveVenuePwaIcons`) и лежат рядом с остальными файлами заведения; `venues.pwa_icons_token` — общий префикс их имён (одна колонка вместо трёх URL, которые обязаны быть согласованы). У maskable содержимое вписано в 80% холста: Android обрезает такую иконку по своей форме, и всё за пределами безопасной зоны исчезло бы вместе с куском логотипа. Для заведений, загрузивших логотип ДО этой правки, иконки догоняются лениво при первом запросе манифеста — иначе фича не работала бы ни у кого до повторной загрузки. **Логотип по внешней ссылке** (у части демо-данных он такой) иконок не даёт: скачивать произвольные URL на сервере ради этого не стоит, такие заведения получают иконку сервиса.
- **Иконки сервиса** — `src/public/icons/app-{192,512,maskable-512}.png`, собираются `npm run build:icons` из брендовой марки (той же, что в `partials/brand.ejs`) и коммитятся. Отдельно стоит знать: `src/public/favicon.svg` — до сих пор логотип из скаффолда, к бренду qr.menu отношения не имеющий; для иконок он не используется, но сам favicon просится к замене.
- **Service worker** — `src/public/sw.js`, область действия `/`, регистрируется только со страниц меню. Вмешивается ТОЛЬКО в `/menu/*`, статику (`/css`, `/js`, `/fonts`, `/icons`) и `/uploads/*`; админка, `/api/events`, `/order`, `/review` и сам манифест идут мимо него нетронутыми. Стратегии: HTML — network-first с таймаутом 3 секунды (гонка «сеть против таймера», а не просто ожидание: зависший на 30 секунд запрос для гостя ничем не лучше отсутствия сети); CSS/JS/шрифты — cache-first с фоновой ревалидацией; фото — cache-first с потолком 120 файлов и 40 МБ на заведение и вытеснением по LRU (порядок ключей Cache API = порядок вставки, повторное обращение перекладывает запись в конец); всё остальное — сеть без кэша. POST не перехватывается никогда.
- **Версия кэша** — `menu_version`, приходит со страницы через `postMessage`, а не через URL регистрации: разные заведения в одном браузере делят одну область действия, и смена URL скрипта перерегистрировала бы воркер туда-сюда на каждом переходе между меню. При смене версии старый HTML-кэш заведения удаляется.
- **Приостановленное заведение** (edge case промта). Network-first уже отдаёт свежую заглушку, но она возвращается с кодом 200 и осела бы в кэше как меню — поэтому сервер помечает заглушку и 404 заголовком `X-Menu-Cacheable: 0`, а воркер такие ответы не кэширует.
- **«Показано сохранённое меню»** — своих заголовков страница о себе прочитать не может, а `navigator.onLine` врёт (телефон в сети без интернета — обычное дело в зале). Воркер, отдав HTML из кэша, ставит отметку в служебном кэше, страница спрашивает состояние через `MessageChannel` и показывает закрываемую ПОЛОСУ (не модалку). При возврате сети полоса исчезает и, если `menu_version` изменилась, страница молча перезагружается один раз.
- **Обновление воркера** без двойной перезагрузки: `install` НЕ вызывает `skipWaiting` сам — сначала вкладка показывает полосу «меню обновилось», и только по нажатию шлёт `SKIP_WAITING`; перезагрузка ровно одна, по `controllerchange` с защитой от цикла. `clients.claim()` — в `activate`.
- **Предложение установки** — второй визит И больше 20 секунд на странице, одно предложение в 30 дней, отказ (в том числе крестиком) запоминается. iOS `beforeinstallprompt` не даёт вовсе, поэтому там показывается короткая инструкция «Поделиться → На экран „Домой“». **iOS определяется на клиенте, а не на сервере**: страница меню кэшируется по `slug+lang`, и признак, вычисленный из User-Agent первого зашедшего, показывался бы всем остальным.
- **Приватный режим** — регистрация и все обращения к `localStorage`/Cache API в `try/catch`: страница обязана работать как обычно, просто без офлайна.
- **Аналитика** — `start_url` несёт `?src=pwa`, `menu_events.source` расширен миграцией, метка разбирается в `eventTracking.detectSource` ДО реферера (у запуска с домашнего экрана его нет, иначе заход считался бы `direct`). Список источников в `analyticsDashboard` жёсткий (он задаёт порядок строк и показывает источники с нулём), поэтому новый источник надо дописывать и туда — это уже сделано.
- **Проверка** — `npm run check:sw` (`scripts/check-sw.js`): 21 проверка логики воркера на поддельном Cache API в Node. Проверяются именно РЕШЕНИЯ: что перехватывается, а что нет; network-first и откат в кэш; отказ кэшировать заглушку; сброс кэша при смене версии; вытеснение фото по LRU до 40 МБ; отсутствие `skipWaiting` при установке. **Чего эта проверка не даёт и что осталось непроверенным:** реальная регистрация воркера в браузере (встроенная панель браузера её блокирует независимо от CSP — проверено отдельно), установка на домашний экран, поведение iOS Safari и реальный офлайн на телефоне.

## Роль официанта: стоп-лист с телефона (промт 3.5)

- **Роль вернулась, права — нет.** `staff` была удалена миграцией `1787502100000_remove-staff-role.cjs`; `1787507500000_restore-staff-role.cjs` заново расширяет оба CHECK на `admins` (сама применённая миграция не трогается). В БД у staff те же поля, что у venue_admin, — всё различие в том, куда его пускают.
- **Права — явный БЕЛЫЙ список маршрутов** (`src/middlewares/staffAccess.js`), один `app.use('/admin', …)` строго до маунтов. Так любой новый раздел админки по умолчанию для официанта закрыт. При списке запретов было бы наоборот: забыл строку — и официант видит цены или подписку. Ошибка в белом списке даёт «не пускает туда, куда надо» (заметно сразу), ошибка в чёрном — «пускает туда, куда не надо» (не заметно никогда). Для всех остальных ролей middleware — проверка одного поля сессии и `next()`. `GET /admin` для staff не 403, а редирект на `/admin/stoplist`: упираться в отказ на собственной стартовой странице ему незачем.
- **Проверка списка — `npm run check:staff-access`** (`scripts/check-staff-access.js`): 42 явных утверждения «должно быть открыто / должно быть закрыто» плюс обход РЕАЛЬНОГО стека роутеров Express, который печатает все маршруты под `/admin` двумя списками. Сейчас открыто 14 (login/logout/lang, свой пароль, стоп-лист и вызовы), закрыто 76. Появился новый раздел — он виден в закрытых при первом же прогоне; попал в открытые по недосмотру — виден там же. Пути с `//` и `..` белый список не матчит и отдаёт 403: whitelist обязан падать закрытым.
- **`/admin/stoplist`** — без сайдбара, своя упрощённая шапка (`partials/staff-header.ejs`). Строки от 56px, переключатель — нативный `checkbox`, уведённый за пределы видимости (клавиатура и скринридер работают, вид рисует соседний `span`). Залипающий поиск, фильтр «только недоступные» со счётчиком, «Вернуть всё в наличие» с подтверждением. Варианты опций переключаются там же, вложенно под позицией. Цены видны, но не редактируются — прятать их бессмысленно, они есть в меню.
- **Сеть и конфликты.** Переключение — `fetch` с оптимистичным обновлением; при ошибке откат. Оффлайн отличается от ошибки сервера: показывается «нет сети, изменение не сохранилось» и кнопка «Повторить», которая повторяет именно то действие. Сервер возвращает ФАКТИЧЕСКОЕ состояние из `RETURNING`, и клиент рисует его, а не свою догадку, — двое официантов на одной позиции получают «последний выигрывает» без ошибки. При возврате вкладки на передний план и при восстановлении сети клиент дёргает `GET /admin/stoplist/state` и перерисовывает переключатели: телефон официанта лежит в кармане часами.
- **«Выключил Азиз, 14:20»** берётся из `admin_action_logs` (`DISTINCT ON` по последней записи `toggle_availability`), а не из отдельной колонки в `items`: журнал и так пишется на каждое переключение, второй источник правды однажды разошёлся бы. Подпись показывается только пока позиция действительно выключена — «Вернуть всё в наличие» пишет ОДНУ сводную запись на всё действие (иначе аудит утонул бы в сотне строк), и без этого условия на уже включённой позиции висело бы враньё.
- **Каждое переключение идёт через `pgNotify.publishMenuChange`** — bump `menu_version` и сброс кэша меню. Без этого гости видели бы выключенную позицию до истечения TTL (прямое требование промта).
- **`/admin/staff`** у venue_admin: список, создание (имя, логин, пароль), деактивация, сброс пароля, потолок 10 ДЕЙСТВУЮЩИХ сотрудников (лимит проверяется и при возврате отключённого в строй — иначе через отключение/включение его можно было бы обойти). Удаления нет вовсе: `admin_action_logs.admin_id` стоит на `ON DELETE RESTRICT` именно затем, чтобы история уволенного осталась читаемой.
- **Быстрый вход** — переиспользованы `password_reset_tokens` с параметром TTL (24 часа вместо часа для восстановления пароля); схема не менялась, `expires_at` там уже был. Ссылка одноразовая, в БД лежит только её хеш, показывается ровно один раз. Владелец копирует её и отправляет сотруднику сам: Telegram официанта сервису неизвестен. Побочный эффект, о котором стоит помнить: выдача приглашения гасит непогашенный токен восстановления пароля этого же человека — так устроен `passwordResetTokenModel.create`, и это правильно.
- **Вызовы официанта** (`/admin/calls`) — список за последние 12 часов и кнопка «Иду». Подтверждение из веба идёт в новую колонку `waiter_calls.acknowledged_by_admin_id`, отдельно от `acknowledged_by_tg_id`: это разные каналы, и складывать их в одну колонку значило бы потерять, откуда пришёл ответ. Идемпотентность та же, что у кнопки в Telegram (`WHERE status = 'new'`) — принятый где-то ещё вызов возвращает `already` и просто перерисовывается, а не даёт ошибку. Новые вызовы подтягиваются опросом раз в 15 секунд.
- **Edge cases.** Заведение в `suspended`/`archived` — вход staff запрещён с понятным текстом (владелец при этом входит: приостановка снимается оплатой изнутри кабинета). Чужое заведение — `venue_id` входит в `WHERE` самого `UPDATE`, поэтому подставленный чужой id даёт 404, а не переключение. Отключённый сотрудник не входит вообще (общая проверка `is_active` при логине).

## Свой домен для заведения (промт 3.7)

- **Схема** — `venue_domains` (`domain text NOT NULL UNIQUE` в нижнем регистре и punycode, `status` из пяти значений, `verification_token`, `verified_at`, `last_check_at`, `last_error`, `is_primary`, `created_at`) плюс две колонки, которых в перечне промта нет: `check_attempts` и `next_check_at`. Без них его же требование «не чаще раза в 5 минут на домен, с экспоненциальным отступом» невыразимо, а держать отступ в памяти планировщика нельзя — он обязан пережить перезапуск процесса. Регистр и форма домена закреплены `CHECK` в БД вторым рубежом: домен в верхнем регистре — тот же домен, и разъехавшийся регистр обошёл бы `UNIQUE`.
- **«Не больше 2 доменов на заведение» — уникальным индексом `(venue_id, is_primary)`, а не подсчётом строк.** Один основной плюс один не-основной и есть максимум два, ровно та формулировка, которой промт объясняет само ограничение. Счёт строк перед вставкой — классическая гонка двух вкладок; индекс не обойти ничем. Заодно бесплатно получается «основной ровно один».
- **Маршрутизация по хосту** (`src/middlewares/customDomain.js`) стоит В САМОМ НАЧАЛЕ цепочки — до статики, сессии и всех маршрутов. Не ради скорости: решение «это домен заведения» меняет всё, что идёт дальше (сессию не подключаем, админку не отдаём, SEO строим на другой адрес), и принимать его посреди цепочки значит принимать дважды. Корень своего домена ОТДАЁТ меню, а не редиректит на `/menu/<slug>`: адрес `menu.mykafe.uz/` должен таким и оставаться, иначе весь смысл своего домена теряется.
- **Кэш доменов** (`src/services/domainCache.js`) — ОДИН снимок всей таблицы активных доменов, а не запись на ключ с TTL, как `menuCache`. Активных доменов на порядки меньше, чем страниц меню, меняются они раз в жизни домена, а просматривать их надо на КАЖДОМ входящем запросе, включая запросы на собственный хост сервиса: кэш промахов при такой нагрузке был бы отдельным механизмом со своей инвалидацией. Инвалидация — через свой канал `NOTIFY domain_changed` рядом с `menu_changed` (события совершенно разной частоты: меню меняется десятки раз в день, домен — раз в жизни). Пока снимок не загружен, запрос ЖДЁТ загрузки, а не получает ошибку: параллельные запросы делят один поход в БД, так что ожидание случается ровно один раз за старт процесса.
- **Сессия на кастомных доменах не подключается вовсе** — `express-session` пропускается для таких запросов. Дело не только в том, что гостю сессия не нужна: иначе `qrmenu.sid` выставлялся бы НА ДОМЕН ЗАВЕДЕНИЯ, то есть сервис раздавал бы идентификаторы своих сессий по чужим зонам. `req.session` там остаётся `undefined`, и публичный путь к этому готов (`isOwnerPreview` проверяет наличие сессии), а всё, что сессию действительно требует, на кастомный домен не попадает — оно отсеяно редиректом.
- **Хост входит в ключ кэша меню и кэша манифеста PWA.** Это была главная ловушка задачи: одно и то же меню на своём домене и на адресе сервиса — РАЗНЫЙ HTML (canonical, hreflang, og:url и `start_url` манифеста указывают на тот адрес, по которому страницу открыли). Без хоста в ключе первый же гость, зашедший через `qr.menu`, закэшировал бы страницу с каноническим адресом сервиса, и её получали бы все, кто пришёл на `menu.mykafe.uz`, — то есть поисковик склеил бы домены ровно наоборот тому, что просит промт. `og:image` от хоста не зависит (там только название заведения) и ключ сохранил прежний.
- **SEO на своём домене** держится на одной паре значений — `baseUrl` и `menuPath` (`menuUrlPartsFor` в `routes/publicMenu.js`): на своём домене меню живёт в КОРНЕ, поэтому `menuPath` там `/`, а не `/menu/<slug>`. Обе величины вычисляются один раз и расходятся во все теги разом, чтобы canonical и hreflang физически не могли разъехаться. У www-алиаса canonical указывает на ОСНОВНОЙ домен пары, иначе две версии страницы конкурировали бы между собой. `sitemap.xml` на своём домене меняет не только адрес, но и СОСТАВ: одна страница вместо лендинга и сотни чужих меню, которых на этом домене не существует.
- **Проверка владения — две независимые вещи, и обе обязательны** (`src/services/domainVerification.js`): домен указывает на нас (CNAME на наш хост или A на наш IP) И владение доказано TXT-записью с выданным токеном. Первое без второго — это захват чужого домена, случайно направленного на наш IP; второе без первого — домен, который не работает. TXT ищется на служебной метке `_qrmenu.<домен>`, а не на корне зоны: там обычно уже живут SPF/DMARC, и просить владельца дописать туда строку — лишний способ сломать ему почту.
- **Отступ и остановка.** Пол — 5 минут на домен (`next_check_at` в БД, а не счётчик в памяти), дальше удвоение до потолка в 2 часа: DNS распространяется часами, и домен, не поднявшийся за два часа между попытками, не поднимется и за четыре. Через 48 часов после добавления — `failed` и уведомление владельцу. Причина неудачи хранится КЛЮЧОМ словаря, а не текстом: `last_error` показывается владельцу на его языке, а язык на момент проверки планировщику неизвестен. Отдельно различаются «в DNS ничего нет», «направлен не к нам», «нет TXT» и «резолвер не ответил» — последнее наша проблема, и выглядеть как вина владельца оно не должно.
- **Планировщик доменов — ОТДЕЛЬНЫЙ** (`bot/worker/domainScheduler.js`, тик раз в минуту). Существующий `worker/scheduler.js` тикает раз в час — верный такт для подписок и напоминаний и бесполезный для «раза в 5 минут». Активные домены перепроверяются раз в 6 часов: промт требует заметить, что заведение убрало запись из DNS, не отключив домен в админке. Такой домен уходит в `failed` через сутки — это 4 неудачи подряд, а не разница дат: `check_attempts` обнуляется при каждой успешной проверке, так что отдельная колонка «когда сломалось» не нужна.
- **Сертификаты: root у скрипта, БД у Node.** `scripts/issue-cert.sh` (systemd-таймер раз в 5 минут, от root) берёт домены в статусе `verifying` — статус И ЕСТЬ очередь, отдельной таблицы задач нет, и «домен ждёт сертификат» не может разойтись с «в очереди есть задача на него». Результат возвращается через `scripts/domain-cert-hook.js`: `activate` переводит домен в `active`, шлёт `NOTIFY domain_changed` и ставит уведомление владельцу; `fail` записывает причину, НЕ переводя в `failed` (выпуск часто не удаётся с первого раза из-за лимитов Let's Encrypt или ещё не разошедшегося DNS — это повод повторить, а не поставить крест). Почему пополам: certbot требует root, приложению root не нужен и не даётся (прямое требование промта), но запись в БД, очередь уведомлений и сброс кэша — логика приложения, и дублировать её в bash через psql значило бы завести вторую расходящуюся реализацию тех же переходов.
- **Автопродление** — `scripts/renew-certs.sh` вместо стандартного `certbot.timer`: тот же график дважды в сутки плюс то, чего в стандартном таймере нет — при неудаче алерт ВЛАДЕЛЬЦУ СЕРВИСА (не заведению: продление сертификата наша работа, и владелец кафе с ней ничего сделать не может). Домен при неудачном продлении НЕ отключается: сертификат обычно действителен ещё несколько дней, и снимать домен раньше срока значит сломать то, что работает.
- **Edge cases.** Заведение в `suspended` — по домену отдаётся та же заглушка, что и на адресе сервиса, а сертификат продолжает продлеваться (это забота nginx и certbot, статусу заведения они не подчиняются). Домен пропал из DNS — `failed` через сутки, уведомление, меню продолжает работать на адресе сервиса. Чужой домен направлен на наш IP без добавления в систему — первым рубежом `default_server` в nginx (см. ниже), но и приложение в одиночку ведёт себя так же: на неизвестном хосте только редирект на сервис, никогда не чьё-либо меню. Домен занят другим заведением — ошибка на этапе ДОБАВЛЕНИЯ, распознаётся по имени нарушенного ограничения, а не отдельным `SELECT` перед вставкой (между таким `SELECT` и `INSERT` домен успевает занять кто угодно). Кириллические домены принимаются и хранятся в punycode, а на экране показываются обратно читаемыми. Собственный адрес сервиса подключить нельзя — заведение, добавившее `qr.menu`, перехватило бы весь сервис на себя.
- **Проверки.** `npm run check:domain-dns` (37 проверок) — нормализация имён, punycode в обе стороны и вся логика проверки владения на ПОДСТАВНОМ резолвере: настоящего DNS у выдуманного домена нет, а зависеть от чужой зоны проверка не должна. `npm run check:custom-domains` (49 проверок) — сквозная, ходит на приложение с подменённым заголовком `Host`, то есть ровно так, как приходит браузер гостя. Клиент там на `node:http`, а НЕ на `fetch`: undici считает `Host` запрещённым заголовком и молча его выбрасывает — запрос уходит на localhost, приложение видит свой собственный хост, и вся проверка проходит вхолостую, показывая зелёные галочки там, где ничего не проверено (эта ловушка сработала при первом прогоне).
- **Чего проверки НЕ дают и что осталось непроверенным:** выпуск сертификата certbot'ом, конфигурация nginx и реальное разрешение DNS. Ни того, ни другого, ни третьего на машине разработки нет — это тот же честный остаток, что и с регистрацией service worker в промте 2.5. Проверено всё, что можно проверить без них: маршрутизация по хосту, редиректы, отсутствие cookie сессии, SEO-теги, разделение кэша между хостами, админка, отступы и переходы статусов.

### Конфигурация nginx

Промт требует описать её подробно, включая обработку неизвестных хостов. Ключевых решений три.

**1. `default_server` обязателен и обязан быть глухим.** Без него nginx отдаёт первый попавшийся
`server`-блок любому хосту, который указали на наш IP, — то есть чужому домену досталось бы
меню случайного заведения. Блок ниже отвечает `421 Misdirected Request` и не проксирует никуда:

```nginx
# Ловушка для всего, что не наш домен и не подключённый домен заведения.
server {
    listen 80 default_server;
    listen 443 ssl default_server;
    server_name _;

    # Самоподписанный сертификат: без него TLS-рукопожатие вообще не состоится, и вместо
    # понятного 421 гость увидит обрыв соединения.
    ssl_certificate     /etc/nginx/ssl/default.crt;
    ssl_certificate_key /etc/nginx/ssl/default.key;

    # ACME пропускаем даже здесь: пока сертификат для нового домена не выпущен, домен
    # приходит именно в default_server, и челлендж обязан работать.
    location /.well-known/acme-challenge/ { root /var/www/acme; }

    location / { return 421; }
}
```

**2. Один общий `server`-блок на все домены заведений, а не блок на домен.** Иначе каждый новый
домен требовал бы правки конфига и `reload` — то есть подключение домена перестало бы быть
самообслуживанием. Список доменов nginx не знает вовсе: он проксирует всё на приложение,
а какому заведению принадлежит хост, решает `middlewares/customDomain.js` по своему кэшу.
Сертификаты подбираются по SNI из общего каталога certbot:

```nginx
server {
    listen 443 ssl;
    http2 on;
    # Перечислять домены не нужно: этот блок принимает всё, что не поймал default_server,
    # то есть все домены, для которых certbot уже выпустил сертификат.
    server_name ~^(?<custom>.+)$;

    ssl_certificate     /etc/letsencrypt/live/$custom/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/$custom/privkey.pem;

    location /.well-known/acme-challenge/ { root /var/www/acme; }

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host              $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    }
}

# HTTP -> HTTPS для доменов заведений, кроме ACME.
server {
    listen 80;
    server_name ~^(?<custom>.+)$;
    location /.well-known/acme-challenge/ { root /var/www/acme; }
    location / { return 301 https://$host$request_uri; }
}
```

**3. `proxy_set_header Host $host` — не мелочь, а условие работы всего.** Приложение отличает
свой хост от домена заведения ровно по этому заголовку; подставь nginx сюда своё имя
(`$proxy_host`), и все домены заведений мгновенно превратились бы в обращения к сервису.
По той же причине в приложении стоит `app.set('trust proxy', 1)`: без него `req.protocol`
всегда `http`, и canonical с og:url уехали бы на `http://` в проде.

**Каталог ACME — общий на все домены** (`/var/www/acme`). Отдельный каталог на домен означал бы
правку nginx перед каждым выпуском, то есть ровно то, чего мы избегаем в пункте 2.

**Таймеры systemd:**

```ini
# /etc/systemd/system/qrmenu-issue-cert.service   (Type=oneshot)
ExecStart=/opt/qrmenu/scripts/issue-cert.sh
Environment=ACME_WEBROOT=/var/www/acme
Environment=CERTBOT_EMAIL=ops@example.com

# /etc/systemd/system/qrmenu-issue-cert.timer
OnBootSec=2min
OnUnitActiveSec=5min
```

Продление ставится вместо `certbot.timer` (его при этом надо выключить, иначе продлевать будут
оба и алерт об ошибке придёт не от того, кто её увидел):

```ini
# /etc/systemd/system/qrmenu-renew-certs.timer
OnCalendar=*-*-* 03,15:24:00
RandomizedDelaySec=1h
```

## Несколько заведений на одном аккаунте (промт 3.6)

- **Схема** — `admin_venues (admin_id, venue_id, role CHECK IN ('owner','manager','staff'), created_at)`, `PRIMARY KEY (admin_id, venue_id)`, индексы по обеим колонкам. Миграция `1787508100000` переносит существующие связи (`venue_admin` → `owner`, `staff` → `staff`) и **сверяет число перенесённых строк** в том же `DO`-блоке через `RAISE EXCEPTION`: миграция, которая молча перенесла не всех, хуже упавшей. `admins.venue_id` НЕ удалена — на неё только повешен `COMMENT` «устарело» (`1787508300000`); удаление отдельной миграцией потом, это защита от невозможности отката. Опциональные `venue_groups` (`1787508200000`) заведены под будущую сводную аналитику сети и пока только хранят связь.
- **Главное решение: `session.admin.venueId` сохранил имя, но сменил смысл** — теперь это АКТИВНОЕ заведение. Так примерно сотня существующих обращений к нему автоматически стала «фильтром по активному заведению». Альтернатива — переименовать и править каждое место — означала бы сотню шансов промахнуться, причём промах был бы невидим и означал утечку данных между заведениями.
- **Доступ проверяется в БД на КАЖДЫЙ запрос** (`src/middlewares/activeVenue.js`), а не берётся из сессии. Сессия живёт неделю, доступ может быть отозван минуту назад, и разница между этими сроками — это и есть окно утечки. Один индексированный запрос по `admin_id` заодно отдаёт список для переключателя, так что отдельной цены у проверки нет. Middleware стоит на `/admin` строго до `staffAccess` и до маунтов маршрутов.
- **Роль — свойство пары (администратор, заведение)**, а не аккаунта: один человек бывает `owner` в одной точке и `manager` в другой. `requireVenueRole(roles)` (`src/middlewares/auth.js`) смотрит на роль в активном заведении; все 27 прежних вызовов `requireRole` переведены на него, кроме трёх суперадминских. `staffAccess` тоже переключён с `admin.role` на `admin.venueRole` — официант, работающий в двух точках сети, в каждой получает ровно свои права. Пункты «Подписка» и «Сотрудники» у `manager` не просто отдают 403, а **не рисуются в меню**: ссылка, гарантированно ведущая в отказ, — дефект сама по себе.
- **Переключатель в шапке** (`partials/venue-switcher.ejs`): одно заведение — просто название, несколько — выпадающий список (тот же `details/summary`, что у остальных меню кабинета, поэтому `dropdown.js` закрывает его теми же правилами), поиск появляется от семи заведений. Каждая строка — отдельная форма `POST /admin/switch-venue` с CSRF-токеном, а не ссылка: смена активного заведения меняет состояние сессии, и делать это по GET нельзя. Параметр `redirect` возвращает на тот же раздел и проходит через `safeRedirect` — только путь, только начинающийся с `/admin`, отдельно отсекаются `//` и обратный слэш, которые браузер трактует как внешний адрес.
- **Изоляция данных — главный риск задачи**, поэтому она проверена эмпирически, а не чтением кода. `npm run check:venue-isolation` (19 проверок) заводит ОДИН аккаунт с ДВУМЯ заведениями и третьим, недоступным, наполняет каждое уникальными строками и, переключаясь, убеждается, что на каждом экране видно только своё, а обращения к чужим сущностям отбиваются и ничего в БД не меняют. Третье заведение отличает «фильтр по активному» от «фильтра по всем моим» — без него такая ошибка была бы незаметна.
- **`venue_id` — в `WHERE` самих мутаций, а не только в предыдущем `SELECT`.** Проверка владения отдельным запросом (`loadOwnItemOr404` и её родня) осталась — она даёт понятный 404, — но каждая мутация теперь ещё и сама себя ограничивает: `items` / `item_option_groups` / `item_options` / `availability_schedules` через подзапрос по `categories` (своей `venue_id` у них нет), `categories` — напрямую. Разница видна ровно там, где она важна: между проверкой и записью сессия может переключиться на другое заведение, а форма — прийти из вкладки, открытой в первом. `npm run check:venue-writes` (27 проверок) дёргает модели НАПРЯМУЮ, в обход роутов, и требует от каждой мутации обеих половин: со своим `venue_id` сработать, с чужим — не сработать и оставить строку нетронутой. Одной половины мало: запрос, не делающий ничего вообще, прошёл бы проверку «чужое отбито».
- **Диагностика `QUERY_AUDIT=1`** (`src/config/queryAudit.js`) — обёртка над `pool.query`, которая пишет в консоль запросы к таблицам заведения без фильтра по нему вместе с местом вызова. Запрос считается ограниченным, только если `venue_id` стоит в `WHERE`, в условии `JOIN`, в списке колонок `INSERT` или в `SET`: выборка вида `SELECT i.*, c.venue_id … WHERE i.id = $1` отдаёт строку любого заведения и обязана быть видна, а не считаться безопасной по одному упоминанию колонки. Это ПОДСКАЗКА, а не защита — ложные срабатывания ожидаемы (запись через `client.query` внутри транзакции обёртка не видит вовсе, а вставки по проверенному родителю честно помечает). Вне разработки выключено жёстко: в `production` переменная игнорируется.
- **«Все заведения»** (`/admin/venues`, пункт появляется только от двух заведений) — таблица «заведение / ваша роль / подписка / до / просмотры за 7 дней / позиций / в стоп-листе / ссылки» одним запросом с `LEFT JOIN LATERAL`: у сети из десяти точек цикл «на каждое заведение три запроса» стоил бы 31 поездку в базу на одну страницу. `admin_id` в `WHERE` — здесь и есть изоляция. Суммарные просмотры рисуются тем же `partials/analytics-bar-chart.ejs`, а раскладка по дням вынесена в `venuePageViewModel.buildDailyBuckets` и переиспользуется дашбордом одного заведения: разъедься логика «от какой полуночи считать дни», и суммы на двух экранах перестали бы сходиться на границе суток. Кнопка «Кабинет» у неактивного заведения — форма переключения, а не ссылка (тот же довод, что у переключателя), и для роли `staff` ведёт сразу на стоп-лист.
- **Копирование меню** (`src/services/menuCopy.js`) — предпросмотр числа категорий и позиций делается GET-ом с параметрами в адресе (ничего не меняет, обновляется перечитыванием, PRG не нужен), само копирование — POST в транзакции с PRG. Цель НЕ берётся из формы: копируется всегда в активное заведение, подменить его нечем. Копирование **добавляет**, а не замещает — существующее меню остаётся на месте, а `sort_order` новых категорий сдвигается за конец имеющихся, чтобы копия не перемешалась с исходным меню. Вместе с позициями едут группы опций и варианты (позиция с обязательным выбором размера, приехавшая без размеров, — не «упрощённая копия», а блюдо, которое нельзя заказать); расписания доступности не копируются намеренно — они привязаны к часам работы конкретной точки. При «не копировать цены» обнуляется и `old_price`, и надбавки вариантов: у бесплатного блюда не должно остаться платного варианта.
- **Фото копируются физически.** `photoService.copyItemPhotoFiles` кладёт БАЙТЫ исходных webp в каталог целевого заведения под новым токеном — не пересжимает (исходники уже нужного размера) и не переиспользует ссылку (удаление в одном заведении сломало бы другое, что промт запрещает прямо). Порядок операций выбран так, чтобы отказ на любом шаге не оставлял мусора: файлы копируются ДО транзакции с запоминанием путей, строки пишутся В транзакции, при откате скопированные файлы удаляются. Обратный порядок оставил бы в БД позиции со ссылками на ещё не существующие картинки. Само копирование пишется в журнал одной записью `entity_type = 'menu_copy'` (миграция `1787508400000`), а не полусотней одинаковых `create`, среди которых не видно, что вообще произошло.
- **Edge cases.** Доступа не осталось ни к одному заведению — отдельная страница `errors/no-venues` с работающей кнопкой выхода (CSRF-токен выставляется вручную: `csrfProtection` до этой страницы не доходит), `/logout`, `/lang` и `/password` при этом продолжают работать, иначе человек застревает без возможности выйти. Активное заведение исчезло из списка (удалено или доступ отозван) — middleware молча переключает на первое доступное, а не роняет 500 и не показывает чужое. Одно заведение — экрана сети нет, и вместо голого 404 показывается объяснение, почему: сюда приходят по закладке, оставшейся с тех пор, когда заведений было больше. Массовые операции и импорт работают только с активным заведением — это прямое следствие того, что `venueId` в сессии и есть активное.
- **Проверка разделов 4 и 5 — `npm run check:venue-network`** (43 проверки): сводка показывает своё и не показывает чужого, предпросмотр считает ровно то, что потом копируется, копия совпадает с оригиналом по ценам и стоп-листу, скопированное фото лежит в каталоге ЦЕЛЕВОГО заведения и **переживает удаление оригинала** (это проверяется реальным удалением файла-источника), обнуление цен доходит до надбавок вариантов, копирование из недоступного заведения и в самого себя отбивается, а видимость экрана и пунктов меню соответствует роли в активном заведении.

## Расписание доступности категорий и позиций (промт 2.3)

- **Схема** — `availability_schedules` (две отдельные nullable-ссылки `category_id`/`item_id` вместо полиморфизма, `CHECK ((category_id IS NULL) <> (item_id IS NULL))`, `days smallint[]` в ISO-нумерации 1=понедельник, `time_from`/`time_to`, `is_active`; индексы по обеим ссылкам), `venues.timezone` (`DEFAULT 'Asia/Tashkent'`) и `categories.schedule_hidden_mode` (`hide|dim|section`, `DEFAULT 'dim'`). Интервалов на сущность может быть несколько; потолок — 10 (`availabilityScheduleModel.MAX_RULES_PER_ENTITY`, не из промта: без него форма превращается в способ положить рендер меню). Отдельного флага «работает по расписанию» нет — его роль играет само наличие правил, одно состояние вместо двух, которые могли бы разойтись.
- **Весь расчёт — `src/services/availability.js`, только на сервере.** Время заведения берётся через `Intl.DateTimeFormat` с `timeZone` (не смещением числом), `hourCycle: 'h23'` — иначе часть реализаций отдаёт «24» вместо «00» в полночь. Неизвестная зона не роняет рендер: падаем на `Asia/Tashkent` и пишем в лог один раз на процесс.
- **Переход через полночь** реализован явно, как требует промт: длительность считается как `to > from ? to - from : to + 24ч - from`, а совпадение проверяется для ДВУХ экземпляров интервала — начавшегося сегодня и начавшегося вчера и ещё идущего. Дни недели относятся ко дню НАЧАЛА: «Пт 22:00–02:00» — это ночь с пятницы на субботу.
- **Круглосуточно без разрывов**: `to == from` означает ровно сутки, а интервал, у которого конец ровно на минуту раньше начала (классический `00:00–23:59`), нормализуется в это состояние ПРИ СОХРАНЕНИИ (`normalizeInterval`). Так дыры в 23:59 не возникает вообще — в отличие от подкручивания сравнения на границе, из-за которого соседние `08:00–11:00` и `11:00–15:00` начали бы пересекаться в 11:00.
- **Приоритет** — расписание позиции ПОЛНОСТЬЮ заменяет расписание категории, а не дополняет его: иначе «завтрак кроме понедельника» было бы невыразимо. Выключенное правило (`is_active = false`) считается отсутствующим, а не запрещающим — галочкой у одного интервала владелец не должен уметь погасить позицию навсегда; про неочевидный итог («все интервалы выключены = доступно всегда») админка предупреждает отдельно.
- **Кэш** — `menuCache.set` принимает четвёртым аргументом потолок жизни записи; `publicMenu.js` передаёт время до ближайшей границы любого интервала заведения (`secondsUntilChange`). Страница, где завтраки заканчиваются в 11:00, физически не может дожить до 11:05. У заведения без расписаний аргумент `null` и TTL остаётся прежним, 5 минут.
- **Показ гостю** — режим берётся у категории и применяется ко всем её позициям, включая те, у которых своё расписание: `dim` (по умолчанию) — приглушённо с подписью «Доступно Пн–Пт 08:00–11:00», кнопка добавления не работает; `hide` — не рендерится ни строка, ни заголовок категории, ни её чипс; `section` — всё недоступное собирается в ОДНУ секцию «Доступно в другое время» внизу (не по секции на категорию — иначе низ страницы стал бы копией всего меню). «Нет в наличии» (ручной рубильник) и «вне расписания» подписываются по-разному, и расписание в подписи важнее: гостю полезнее узнать, что блюдо бывает по утрам.
- **Меню целиком вне расписания** — `partials/menu-closed-note.ejs`: «Сейчас меню недоступно. Откроем в 08:00». Партиал, а не кусок `menu.ejs`, потому что нужен в двух местах: над списком в режиме `dim` и ВМЕСТО списка в режиме `hide`, где секций на странице не остаётся вовсе. Во втором случае он вытесняет обычное «меню пустое» — это разные новости, и путать их нельзя.
- **Прямая ссылка на блюдо** (`?item=<id>`) вне расписания открывает карточку с подписью «Доступно Пн–Пт 08:00–11:00», а не «позиции больше нет»: `menuData` на клиенте строится из `allItems` (все позиции), а не из видимых групп.
- **Заказы.** `orderPricing.recomputeOrder` проверяет расписание тем же правилом и возвращает `item_out_of_schedule`. Промт 2.3 про заказы не говорит, но промт 2.4 требует пересчёта «по актуальным ценам И доступности» — без этого гость, положивший завтрак в корзину в 10:59, отправлял бы его в 11:05. Сообщение гостю при этом отдельное (`schedules.errorCartOutOfSchedule`): общее «меню изменилось» на завтраке в час дня выглядит как поломка сайта.
- **Админка** — общий партиал `partials/schedule-editor.ejs` в форме категории и в форме позиции. Формы расписания там СОСЕДНИЕ, а не вложенные: вложенные `<form>` запрещены в HTML (тот же приём, что у групп опций в промте 2.1). Есть переключатель «доступно всегда / по расписанию», чипсы дней (нативные чекбоксы, работают с клавиатуры), время, 4 пресета кнопками (только заполняют поля — `public/js/schedule-editor.js` не сохраняет и не считает ничего), бейдж «сейчас доступно / недоступно» в часовом поясе заведения и предупреждения при пересечении интервалов. У позиции без своих интервалов показывается, какому расписанию категории она сейчас подчиняется. Всё мутирующее — `/admin/schedules/*` с проверкой владения в SQL и записью в `admin_action_logs` с `entity_type = 'schedule'`.
- **Часовой пояс** правит только суперадмин (карточка заведения) — это защита от неверно настроенного сервера, а не настройка владельца; рядом показывается текущее локальное время заведения, чтобы опечатку в названии зоны было видно сразу. Сохранение сбрасывает кэш меню: отрисованная страница посчитана по старой зоне.
- **Самопроверка** — `npm run check:availability` (`scripts/check-availability.js`): 40 проверок на переход через полночь, стык недели, круглосуточный интервал, ближайшую границу для кэша, часовой пояс и предупреждения. Не юнит-тесты (раннера в проекте нет), а прогоняемый вручную набор именно тех случаев, которые промт называет обязательными.

## Аналитика (промт 3.2)

- **Схема** — `menu_events` (сырые события, 180 дней, индексы `(venue_id, created_at)` и `(venue_id, event_type, created_at)`, партиционирование — только комментарий в миграции, не реализовано), `menu_stats_daily` (дневные агрегаты, `UNIQUE(venue_id, stat_on, metric, dimension)`, схема "metric+dimension" вместо колонки на каждый срез — новый разрез не требует миграции), `admin_session_hashes` (для «не учитывать мои просмотры», см. ниже), `venues.exclude_owner_views`/`venues.weekly_summary_enabled` (оба `DEFAULT true`). `venue_page_views` (счётчик из более раннего промта) не тронута и продолжает жить независимо — `page_view` пишется в `menu_events` в той же точке `publicMenu.js`, но **не выводится из агрегатов**, как буквально просит промт: оба источника заполняются параллельно на одном и том же условии, дашборд аналитики целиком читает `menu_stats_daily`, старый дашборд `/admin` — по-прежнему `venue_page_views`. Так проще и без риска пересчитать существующий экран, но при явном запросе на деривацию `venuePageViewModel.getStats()` придётся переписать поверх новой таблицы.
- **Приватность** — `session_hash = SHA-256(SESSION_SECRET + сутки UTC + IP + User-Agent)` (`src/utils/sessionHash.js`, отдельная функция от `utils/hashIp.js` — та хеширует только IP, для другой цели). Сырые IP/User-Agent нигде не сохраняются. В футере публичного меню — короткая строка про обезличенную статистику (`publicMenu.analyticsDisclosure`).
- **Сбор** — `page_view` пишется сервером в момент рендера (`publicMenu.js`), не клиентом: блокировщики рекламы иначе срезали бы главную метрику. Источник перехода определяется на сервере: `?src=qr` (только у ссылки, зашитой в `/admin/qr.png`, — обычная ссылка «Поделиться» этой метки не несёт) → `qr`, `Referer` с известного соцсеть-домена → `social`, свой же домен (переключение категории/языка) → `direct`, любой другой внешний домен → `link`, пустой `Referer` → `direct`. Остальные 14 типов событий шлёт клиент: `src/public/js/event-tracker.js` копит их и отправляет пачкой через `navigator.sendBeacon` на `POST /api/events/:slug` — не чаще раза в 5 секунд и всегда на `pagehide`/`visibilitychange`. Точки вызова — по одной строке в уже существующих обработчиках `public-menu.js` (категории/поиск с debounce 600мс/переключение языка/копирование wifi/«поделиться»), `menu-cart.js` (`item_add`/`item_remove` — только переход через ноль, не каждый тап по степперу; `cart_open`), `dish-card.js` (`item_view`). `order_sent`/`waiter_call` шлёт `order-flow.js` (промт 2.4), `review_prompt`/`review_submit` — `review-flow.js` (промт 3.3, оценка едет в `value`).
- **`POST /api/events/:slug`** (`src/routes/apiEvents.js`) — venue_id намеренно резолвится из `:slug` в URL, а не берётся из тела запроса: иначе любой мог бы приписать события чужому заведению, поменяв число в JSON. Без CSRF (как весь `/menu`) — гость анонимен, `sendBeacon` с `Blob('application/json')` физически не может добавить кастомный заголовок. Каждый элемент пачки валидируется по отдельности (`eventValidators.js` + `eventTracking.filterValidEvents`) — невалидная/неизвестная запись отбрасывается молча, не роняя всю пачку. Лимиты: 100 событий на запрос (в схеме), 500/`session_hash`/час и 2000/IP/час (`middlewares/rateLimit.js`) — ответ всегда `204`, клиент (фоновый beacon) его не читает.
- **Агрегация** — часовой тик существующего планировщика бота (`bot/worker/scheduler.js` → `analyticsAggregation.runHourlyTick()`) пересчитывает вчера+сегодня для каждого заведения, у которого вообще были события (не для всех заведений подряд), и UPSERT'ит `menu_stats_daily` — идемпотентно, повторный запуск не задваивает. Следом — чистка `menu_events` старше 180 дней пачками по 5000 строк.
- **«Не учитывать мои просмотры»** — так как `menu_stats_daily` хранит только счётчики (без `session_hash`), исключение владельца считается **на агрегации**, а не на чтении: на каждый запрос авторизованного `venue_admin` (`middlewares/auth.js`) пишется тот же `session_hash`, что посчитался бы для этого запроса как для гостя (`admin_session_hashes`). Если за день у заведения был хоть один такой hash, агрегация считает метрики ДВАЖДЫ — как есть и с исключением этих hash — и пишет второй набор под префиксом `owner_excluded:`; если владелец в этот день не заходил, второй проход не считается вообще (в подавляющем большинстве дней он не нужен). Дашборд (`analyticsDashboard.js`) читает `owner_excluded:`-метрики, где они есть, и молча падает на обычные там, где владелец не заходил — оба набора всегда совместимы (там, где GROUP BY не вернул бы строку для полностью исключённого измерения, агрегация дописывает явный ноль, иначе чтение приняло бы отсутствие строки за «не изменилось»). Переключатель — на самой странице аналитики, вступает в силу со следующего часового тика, не мгновенно.
- **Экран `/admin/analytics`** — период 7/30/произвольный (обычные `?period=`/`from=`/`to=` в URL, без скрытого состояния — ссылку можно сохранить). «Мало данных» — общий порог 20 просмотров за период на всю страницу графиков/списков, а не по каждому блоку отдельно. Графики — вручную на SVG (`src/views/partials/analytics-bar-chart.ejs`, координаты считаются на сервере), тултип по наведению/тапу — `src/public/js/analytics-charts.js`. «Смотрят, но не берут» — эвристика (не из промта дословно): не меньше 3 просмотров за период и доля добавивших не выше 20%. Топ столов по заказам показывается только если для него есть данные (появятся вместе со столами в 3.4).
- **Экспорт и сводка** — `GET /admin/analytics/export.xlsx` строит `.xlsx` (библиотека `exceljs` — из тех же уже посчитанных данных дашборда, не отдельным запросом) через `analyticsExport.js`. Еженедельная сводка — понедельник, UTC (`bot/worker/scheduler.js`, `dedupKey` по началу недели, а не по номеру ISO-недели — тот же эффект без отдельной арифметики), только если у заведения есть `owner_telegram_id` и включён `weekly_summary_enabled`; кнопка «Открыть аналитику» — `Markup.button.url`, тот же приём, что и у карточки заявки на оплату.

## Отзывы: сбор и уход на карты (промт 3.3)

- **Схема** — `reviews` (оценка 1–5, необязательные `comment`/`contact`, `table_id`, `lang`, `session_hash`, `went_external`/`external_target`, `status` из `new|read|resolved|spam`, `owner_reply`/`replied_at`, `is_suspicious`; индексы `(venue_id, created_at)`, `(venue_id, status)`), плюс поля заведения: `reviews_enabled` (`DEFAULT false`), `google_review_url`, `yandex_review_url`, `reviews_prompt_delay_sec` (`DEFAULT 45`, CHECK 0–3600), `reviews_threshold` (`DEFAULT 4`, CHECK 1–5). Существующее `address_2gis_url` не тронуто — это «как доехать», к отзывам отношения не имеет.
- **Что попадает в кэшируемый HTML** — только `reviews_enabled` как признак уровня заведения. «Показывать ли приглашение ИМЕННО этому гостю» решает `GET /review/:slug/context` (`Cache-Control: no-store`) — тот же приём, что и с номером стола в промте 2.4: страница меню кэшируется по `slug+lang`, и всё гостевое в неё зашивать нельзя. Если сбор выключен или заведение `suspended`/`archived`/`is_active=false`, контекст отвечает только `{available:false}` — ни задержки, ни порога, ни ссылок.
- **Поток гостя** (`src/public/js/review-flow.js`) — карточка «Как вам у нас?» внизу страницы через `reviews_prompt_delay_sec` секунд ИЛИ сразу после отправки заказа (событие `qrmenu:order-sent` из `order-flow.js` — прямого вызова нет, `review-flow.js` может быть вообще не подключён). Пока открыт любой `<dialog>`, показ откладывается: под модалкой карточку всё равно не видно. Звёзды — нативные `radio` с CSS: разметка идёт от 5 к 1, `flex-direction: row-reverse` возвращает их на экране в порядок 1..5, и это единственный способ подсветить «все до выбранной» чистым CSS (селектор `~` смотрит только вперёд по разметке); плата — стрелки клавиатуры внутри группы идут справа налево, поэтому у каждой звезды есть явная подпись «3 из 5».
- **Две ветки, обе с кнопками карт** — разметка одна, класс `is-high`/`is-low` на теле модалки меняет только `order` блоков и акцент кнопок. Высокая оценка: крупные кнопки «Отзыв в Google»/«Отзыв в Яндексе» плюс необязательное «что понравилось». Низкая: сначала «что пошло не так» и заметная кнопка отправки, под разделителем — те же кнопки карт, спокойнее по акценту. Прятать или блокировать их нельзя ни в одной ветке: это прямо запрещено правилами площадок и просто нечестно по отношению к гостю. Кнопок нет только тогда, когда соответствующая ссылка не заполнена.
- **Один запрос на отзыв, без потерь** — клик по кнопке карт не ждёт ответа сервера (браузер уже открывает вкладку): если отзыв ещё не отправлен, `navigator.sendBeacon` создаёт его тем же запросом вместе с отметкой о переходе (`external` в теле `POST /review/:slug`), если уже отправлен — уходит только отметка в `POST /review/:slug/external`. Так 5 звёзд от гостя, который сразу ушёл на Google, не теряются, и внутреннее среднее не перекашивается в сторону тех, кто дописал жалобу.
- **Защита от накрутки** — один `session_hash` на заведение раз в 30 дней (проверка в БД, а не только в `localStorage`: его чистят в один клик), 20 отзывов с IP в сутки (`middlewares/rateLimit.js`, как лимит заказов в 2.4 — `session_hash` считается от IP+UA и IP обратно из него не достать), отзывы без текста и с тем же текстом, что предыдущий, помечаются `is_suspicious` автоматически. Ничего не удаляется и не прячется — решение принимает владелец.
- **Рейтинг в карточке заведения** — источник ровно один (`publicMenu.js:resolveRating`): если сбор включён И внутренних оценок не меньше 5, показывается их среднее с честной подписью «Оценки гостей в меню»; иначе — ручные `venues.rating`/`review_count` суперадмина. Никогда не складываются. Тот же результат уходит в `aggregateRating` JSON-LD, чтобы поисковик и гость видели одно число. Отзывов нет — блок рейтинга скрыт целиком, «0.0» не показывается. Значение живёт в кэшируемом HTML (TTL 5 минут); специально сбрасывать кэш на каждый гостевой отзыв не станем — на людном заведении это обнуляло бы кэш постоянно. Кэш сбрасывается на действиях владельца, которые меняют правило: включение/выключение сбора и пометка отзыва спамом (спам исключается из среднего). В суперадминке рядом с полями ручного рейтинга написано, используются ли они сейчас и что реально стоит в карточке.
- **`/admin/reviews`** — статистика, настройки (переключатель, ссылки с пошаговой инструкцией, где их взять, задержка, порог), предпросмотр обеих веток теми же CSS-классами, что и на публичной странице, и список с фильтрами по статусу и оценке. Действия «прочитано»/«решено»/«спам» и заметка для себя пишутся в `admin_action_logs` с `entity_type = 'review'` (отдельная миграция на CHECK). `venue_id` входит в `WHERE` самого `UPDATE`, а не только в шаблон. Возврат после действия строится из уже разобранных фильтров, не из `Referer`. Бейдж непрочитанных — `middlewares/reviewsBadge.js`, один `app.use('/admin', …)` до маршрутов, чтобы число было видно на любой странице кабинета (как `leadsBadge` в суперадминке).
- **Уведомления** — оценка ниже порога уходит владельцу немедленно через `venueLifecycle.notifyVenue` (личный Telegram → email заведения → владелец сервиса как «нужен ручной контакт»), `dedupKey: review_low:<id>`. У шаблона `review_low_rating` есть и email-рендер (`src/views/emails/review-low-rating.ejs`) — в отличие от остальных `notifyVenue`-шаблонов: заведение без привязанного Telegram это сообщение терять не должно. Высокие оценки владельца не дёргают — они приходят строкой в еженедельной сводке аналитики (`bot/worker/scheduler.js`).

## Мультиязычность (RU/UZ/EN)

- Словари интерфейса: `src/i18n/ru.json`, `src/i18n/uz.json`, `src/i18n/en.json` — все три содержат один и тот же набор ключей (проверяется вручную, автотеста на это нет), хелпер `t(key, lang, params)` и `SUPPORTED_LANGS`/`LANG_FALLBACKS` — в `src/i18n/index.js`.
- В шаблонах доступны `t(key, params)` и `lang` через `res.locals` — глобальный дефолт (`ru`) выставляет `src/middlewares/locale.js`, для `/admin/*` и `/superadmin/*` его переопределяет `src/middlewares/adminLocale.js` по cookie `admin_lang`. Переключатель языка админки (`GET /admin/lang?lang=ru|uz|en&redirect=/путь`) работает для любого администратора независимо от того, какие языки включены у его заведения — это язык интерфейса, а не языки меню для гостей.
- **Языки меню конкретного заведения** — отдельная настройка, не совпадает с языком интерфейса админки: `venues.enabled_langs` (минимум один язык, всегда включает `lang_default`) и `venues.lang_default`, оба редактируются в `/admin/venue-settings` в блоке «Языки для гостей». Нельзя выключить язык, который сейчас является языком по умолчанию — сначала нужно сменить дефолт (проверяется и в форме, и в CHECK-ограничении в БД).
- Название/описание категорий, позиций и профиля заведения хранятся в БД по колонке на язык (`_ru`/`_uz`/`_en`) — `_ru`/`_uz` обязательны, `_en` всегда nullable (существующие заведения не обязаны переводить). Подстановка нужного языка с фолбэком по цепочке (`ru→uz→en`, `uz→ru→en`, `en→ru→uz`) — одна функция `pickLocalized(row, field, lang)` в `src/utils/localize.js`, доступна во всех EJS-шаблонах напрямую (зарегистрирована в `app.locals`). Поля `_en` в формах позиций/категорий показываются, только если у заведения включён английский.
- В списке позиций — приглушённый бейдж «EN» у непереведённых на английский (если он включён), баннер «переведено X из N» и фильтр «показать без перевода на EN» (`?untranslated=en`), без отдельного SQL-запроса — считается по уже загруженным данным.
- Публичная страница меню (`/menu/:slug`): язык — `?lang=` в URL > cookie `menu_lang` > `Accept-Language` браузера > `venues.lang_default`, на каждом шаге пропускается язык, не входящий в `enabled_langs` заведения — если гость запросил выключенный язык, молча получает дефолтный, без редиректа и ошибки. Переключатель на странице рендерится только для включённых языков и пропадает совсем, если включён один. Кэш учитывает язык в ключе (`slug:lang`), так что все версии кэшируются независимо — как HTML-страница, так и og:image-превью (подпись на превью тоже на языке страницы).
- SEO: `hreflang` на странице и `xhtml:link`-альтернативы в `sitemap.xml` перечисляют только включённые у заведения языки (плюс `x-default` на канонический адрес).
