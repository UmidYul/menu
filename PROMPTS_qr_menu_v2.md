# qr.menu — промты для второй волны разработки

Файл содержит готовые промты для ИИ-агента. Каждый промт самодостаточен, но **перед любым промтом нужно вставить блок «Общие правила»** из раздела 2 — в нём ограничения, которые агент обязан соблюдать всегда.

Порядок выполнения важен: промты сгруппированы по блокам, внутри блока идут по зависимостям. Не начинай блок 2, пока не закрыт блок 0.

## 1. Согласованные решения (контекст для тебя, не для агента)

| Вопрос | Решение |
|---|---|
| Регистрация заведений | Заявка через Telegram-бота (основной канал) или форму на сайте. Публикацию подтверждает суперадмин вручную. |
| Оплата | Только вручную: перевод на карту. В админке — экран с реквизитами и кнопка «Я оплатил», подтверждение суперадмином через бота. Модуль спроектирован так, чтобы при появлении ИП вместо реквизитов подставился Click/Payme без переписывания логики. |
| SMS | Не используем нигде. |
| Почта | SMTP доступен. Используем для восстановления пароля и дублирования критичных уведомлений. |
| Отзывы | Google Maps и Яндекс Карты. 2GIS остаётся только как «как доехать». Мягкая схема: обе кнопки видны всем, при низкой оценке сначала предлагается написать владельцу. |
| Рейтинг в карточке | Считается из внутренних отзывов, если их ≥5 и сбор включён. Иначе — ручное значение из суперадминки как фолбэк. Источники никогда не смешиваются. |
| Бот | Один бот сервиса, отдельный Node-процесс. Заведение добавляет его в свою группу и привязывает кодом. |
| Жизненный цикл подписки | draft → trial (30 дней с момента публикации) → active → grace (5 дней) → suspended → archived (через 90 дней). На suspended страница меню не исчезает: показывает название и телефон. |
| Защита от мусора | Заявка ≠ публикация. Триал стартует в момент публикации. Один Telegram-аккаунт — одно заведение. |
| Кэш меню | Инвалидация между процессами через Postgres LISTEN/NOTIFY + `venues.menu_version`. |
| Хранение фото | Локальный диск на выделенном сервере. Объектное хранилище не нужно. |
| Языки | Добавляем EN третьим. Делаем в начале, пока новых таблиц немного. |

## 2. Общие правила (вставлять перед каждым промтом)

```
ОБЩИЕ ПРАВИЛА ПРОЕКТА qr.menu — соблюдай их в любой задаче.

СТЕК И СТРУКТУРА
- Node.js 20+, Express 4, EJS (серверный рендеринг), PostgreSQL, node-pg-migrate,
  express-session + connect-pg-simple, zod, multer + sharp, bcrypt, qrcode.
- src/routes — маршруты, src/controllers — обработчики, src/models — SQL, src/services — сервисы,
  src/middlewares, src/views (EJS), src/public (css/js), src/i18n, src/config, src/validators, src/utils.
- migrations/ — node-pg-migrate, файлы .cjs, имя вида <timestamp>_<kebab-name>.cjs. Новые миграции
  нумеруй строго больше последней существующей. Никогда не редактируй уже применённые миграции.
- Каждая миграция обязана иметь рабочий exports.down. Проверяй, что up → down → up проходит без ошибок.
- Приложение развёрнуто на выделенном сервере, один Node-процесс для веба и отдельный для бота.
  Фото хранятся на локальном диске в public/uploads/:venue_id/ — эту схему не меняй.

ДИЗАЙН
- НИКАКИХ новых цветовых значений. Только существующие CSS-переменные дизайн-системы
  (--primary, --primary-dark, --ink, --muted, --paper, --background, --border, --sage и остальные,
  что уже объявлены в src/public/css/design-system.css). Новые классы можно, новые цвета — нет.
- Шрифты не менять: --font-serif (Playfair Display) для заголовков, --font-sans (Manrope) для текста.
  Шрифты самохостятся, никаких подключений с CDN.
- Иконки — только из src/views/partials/icon.ejs. Если нужной нет, добавь в том же стиле:
  stroke-based, viewBox 24x24, currentColor, без заливок.
- Никаких inline-стилей. Весь CSS — в design-system.css, весь JS — в файлах src/public/js/.
  Единственное исключение — вёрстка писем, там inline-стили обязательны.
- Никаких внешних библиотек, CDN, шрифтов, аналитики и трекеров на клиенте.
- Адаптив от 320px. Тач-цели не меньше 44x44px. Поддержка prefers-reduced-motion во всех анимациях.
- Новые страницы админки собирай из существующих партиалов admin-sidebar.ejs / admin-topbar.ejs
  и уже существующих классов форм — визуально они должны быть неотличимы от venue-settings.ejs.
- Анимации только по transform и opacity. Никаких анимаций layout-свойств.

ТЕКСТЫ И ЯЗЫКИ
- Ни одной строки текста хардкодом. Всё через t('ключ') с добавлением ключей ОДНОВРЕМЕННО
  во все словари: src/i18n/ru.json, src/i18n/uz.json (и en.json после того, как он появится).
- Не оставляй русский текст в узбекском и английском словарях как заглушку — переводи.
- Ошибки валидации zod хранят в message КЛЮЧ словаря, а не готовый текст, — переводятся в роуте.
- Тексты для пользователя пиши по-человечески, без канцелярита.

БЕЗОПАСНОСТЬ И КАЧЕСТВО
- Все SQL — параметризованные запросы, никакой конкатенации строк.
- Любой вход пользователя валидируется через zod до попадания в модель.
- Все маршруты админки — за requireAuth и requireRole. Проверяй, что venue_admin не может
  обратиться к чужому venue_id: сверяй с сессией в самом SQL-запросе, а не только в шаблоне.
- Все изменяющие действия логируй через adminActionLogModel.logAction. Если нужен новый
  entity_type — расширь CHECK-ограничение отдельной миграцией
  (см. образец 1787503200000_alter-admin-action-logs-add-site-settings-entity.cjs).
- POST-формы защищены от повторной отправки: PRG (redirect после успешного POST).
- Rate-limit на все публичные POST-эндпоинты (express-rate-limit уже подключён).
- Никаких секретов в коде. Всё через process.env, с обновлением .env.example и README.
- Комментарии на русском там, где решение неочевидно. Пустых комментариев-описаний не надо.

ПОРЯДОК РАБОТЫ
1. Сначала прочитай файлы, которых касается задача, и покажи план: список файлов,
   схему изменений БД, риски.
2. Дождись подтверждения.
3. Реализуй поэтапно, после каждого этапа — короткий отчёт, что изменилось.
4. В конце обнови README (раздел про эту функцию) и .env.example, если появились переменные.
```

## Промт 0.1 — Инфраструктура: кэш между процессами, очередь уведомлений, почта, конфиг

```
Задача: подготовить инфраструктуру, на которую опираются все последующие функции — корректная
инвалидация кэша между процессами, единая очередь уведомлений, отправка почты, расширение конфига.

────────────────────────────────
1. ВЕРСИОНИРОВАНИЕ И ИНВАЛИДАЦИЯ КЭША МЕНЮ
────────────────────────────────
Проблема: src/services/menuCache.js хранит HTML в Map в памяти процесса. Скоро появится отдельный
процесс Telegram-бота, который тоже сможет менять данные (стоп-лист, статусы подписки).
Инвалидация из одного процесса не дойдёт до другого — гости будут видеть устаревшее меню до
истечения TTL.

Решение:
- Миграция: добавить в venues колонку menu_version integer NOT NULL DEFAULT 1.
- Создать src/models/menuVersionModel.js с функцией bump(venueId): атомарно
  UPDATE venues SET menu_version = menu_version + 1 WHERE id = $1 RETURNING menu_version.
- Вызывать bump везде, где сейчас вызывается сброс кэша меню: сохранение категорий, позиций,
  настроек заведения, загрузка и удаление фото. Найди ВСЕ такие места и не пропусти ни одного.
- Постгресовый NOTIFY: после bump выполнять NOTIFY menu_changed, '<venue_id>'.
  Создать src/services/pgNotify.js — отдельное долгоживущее подключение pg.Client (НЕ из пула:
  пул забирает и возвращает соединения, LISTEN на нём работать не будет), которое делает
  LISTEN menu_changed и при событии вызывает menuCache.invalidate(venueId).
- Обработать обрыв соединения: при error/end переподключаться с экспоненциальной задержкой
  (1s, 2s, 4s … максимум 30s) и заново выполнять LISTEN. При переподключении ПОЛНОСТЬЮ очищать
  локальный кэш, потому что за время обрыва события были потеряны.
- TTL 5 минут оставить как страховку на случай, если NOTIFY не сработал.
- menuCache.invalidate должен принимать venue_id и сбрасывать все языковые варианты заведения.
  Сейчас ключ — slug:lang; если слаг менялся, старый ключ останется висеть. Храни в значении
  кэша ещё и venue_id, чтобы инвалидировать по нему, а не по слагу.

Edge cases:
- Заведение переименовало slug — старый ключ обязан быть сброшен.
- БД недоступна на старте процесса — pgNotify не должен ронять приложение, только логировать
  и пытаться переподключиться.
- Инвалидация должна быть идемпотентной: двойной вызов не ошибка.
- Не отправляй NOTIFY внутри транзакции, которая может откатиться, — иначе кэш сбросится
  под данные, которых нет. Отправляй после успешного COMMIT.

────────────────────────────────
2. ЕДИНАЯ ОЧЕРЕДЬ УВЕДОМЛЕНИЙ (OUTBOX)
────────────────────────────────
Веб-процесс должен уметь отправлять сообщения в Telegram, но бот живёт отдельным процессом.
Прямые HTTP-вызовы между процессами делать не будем — сделаем таблицу-очередь.

Миграция: таблица notifications
- id, channel text NOT NULL CHECK (channel IN ('telegram','email')),
- recipient text NOT NULL (telegram chat_id или email-адрес),
- template text NOT NULL (ключ шаблона, например 'payment_claim_created'),
- payload jsonb NOT NULL DEFAULT '{}',
- lang text NOT NULL DEFAULT 'ru',
- status text NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','sent','failed','skipped')),
- attempts integer NOT NULL DEFAULT 0,
- last_error text,
- scheduled_at timestamptz NOT NULL DEFAULT now(),
- sent_at timestamptz,
- dedup_key text,
- created_at timestamptz NOT NULL DEFAULT now().
- Частичный уникальный индекс на dedup_key WHERE dedup_key IS NOT NULL AND status <> 'failed' —
  чтобы одно и то же напоминание не ушло дважды.
- Индекс (status, scheduled_at).

Модель src/models/notificationModel.js: enqueue(...), claimBatch(limit) с блокировкой
SELECT ... FOR UPDATE SKIP LOCKED (чтобы два воркера не взяли одну запись), markSent, markFailed.

Правила ретраев (задокументируй комментарием, реализация — в промте 1.1):
- максимум 5 попыток, задержки 1м, 5м, 15м, 1ч, 6ч;
- после 5 неудач — status = 'failed' и алерт владельцу сервиса;
- если получатель заблокировал бота (Telegram 403) — сразу 'skipped', без ретраев.

────────────────────────────────
3. ОТПРАВКА ПОЧТЫ
────────────────────────────────
- Добавить зависимость nodemailer.
- src/services/mailer.js: транспорт из ENV (SMTP_HOST, SMTP_PORT, SMTP_SECURE, SMTP_USER,
  SMTP_PASS, MAIL_FROM, MAIL_FROM_NAME), функция send({ to, subject, html, text }).
- Письма собираются из EJS-шаблонов в src/views/emails/*.ejs. Обязательно и HTML, и текстовая версия.
- Вёрстка писем: таблицы, инлайн-стили (единственное разрешённое место — почтовые клиенты иначе
  не умеют), максимальная ширина 600px, без внешних картинок и шрифтов. Цвета те же, что в
  дизайн-системе, но вписаны значениями, потому что CSS-переменные в письмах не работают.
  Логотип — текстом, не картинкой.
- Базовый layout: шапка с названием сервиса, тело, футер с контактами из site_settings
  и строкой «это автоматическое письмо, отвечать на него не нужно».
- Если SMTP не сконфигурирован — send не падает, а логирует предупреждение и возвращает
  { skipped: true }. Локальная разработка не должна требовать SMTP.
- Настрой SPF и DKIM на домене отправки и опиши это в README: без них письма уйдут в спам,
  и восстановление пароля перестанет работать на практике, хотя технически будет исправным.

────────────────────────────────
4. КОНФИГ
────────────────────────────────
- Создать src/config/env.js, который на старте валидирует переменные окружения через zod
  и падает с понятным сообщением, если обязательной нет.
- Разделить обязательные и опциональные: без DATABASE_URL и SESSION_SECRET приложение
  не стартует; без SMTP_* и BOT_TOKEN — стартует с предупреждением и отключёнными функциями.
- Добавить APP_BASE_URL (публичный адрес сервиса) — он нужен для ссылок в письмах и в боте,
  где нет req и нельзя собрать адрес из заголовков.
- Обновить .env.example со всеми переменными и комментариями на русском.

────────────────────────────────
DEFINITION OF DONE
────────────────────────────────
- npm run migrate:up и migrate:down проходят чисто.
- Изменение позиции в админке инвалидирует кэш, и это видно в логах второго процесса.
- Обрыв соединения LISTEN восстанавливается автоматически, кэш при этом чистится.
- notifications.enqueue вызывается хотя бы из одного места и запись появляется в таблице.
- README дополнен разделом про кэш, очередь уведомлений и настройку почты.
```

────────────────────────────────
2. СХЕМА БД
────────────────────────────────
Миграция:
- items: name_en, description_en, composition_en (text, nullable).
- categories: name_en.

- Важно: name_en делаем NULLABLE, в отличие от name_ru/name_uz, которые NOT NULL. Заставлять
  существующие заведения заполнять английский нельзя.

────────────────────────────────
3. ПОВЕДЕНИЕ
────────────────────────────────
- SUPPORTED_LANGS в src/i18n/index.js становится ['ru','uz','en'], создаётся src/i18n/en.json

  этого заведения. Если включён один язык — переключатель не рендерится вообще.
- Если гость пришёл с ?lang=en, а у заведения английский не включён — отдаём lang_default,
  без редиректа и без ошибки.
- Определение языка при первом заходе: ?lang= > cookie menu_lang > Accept-Language (пересечение

- Админка заведения: переключатель «какие языки показывать гостям» в venue-settings.

- Индикатор незаполненного перевода: если заполнено name_ru, но пусто name_en при включённом

- Баннер в админке при включении английского: «включён английский, переведено 0 из N позиций».

EDGE CASES

DEFINITION OF DONE: переключение на EN работает на демо-заведении, hreflang корректны,

# БЛОК 1. Воронка: от заявки до денег

## Промт 1.1 — Telegram-бот сервиса: каркас

```
Задача: создать Telegram-бота сервиса как отдельный процесс. Это несущая конструкция для
регистрации, уведомлений, подтверждения оплат, заказов и алертов.

────────────────────────────────
1. АРХИТЕКТУРА
────────────────────────────────
- Отдельный процесс, точка входа bot/index.js, скрипты "bot": "node bot/index.js" и
  "bot:dev": "node --watch bot/index.js" в package.json.
- Библиотека: telegraf.
- Бот переиспользует src/config/db.js, src/models/*, src/i18n. Не дублируй SQL — если нужного
  метода в модели нет, добавь его в модель, а не пиши запрос в боте.
- Два режима через ENV BOT_MODE: 'polling' для локальной разработки и 'webhook' для продакшена.
  В режиме webhook бот поднимает собственный маленький Express-сервер на BOT_PORT и регистрирует
  вебхук по BOT_WEBHOOK_URL с секретным путём из BOT_WEBHOOK_SECRET. Проверяй заголовок
  X-Telegram-Bot-Api-Secret-Token — без него запрос отбрасывается.
- Бот НЕ должен уметь менять данные меню (позиции, цены, категории) — кроме стоп-листа, который
  появится позже и будет проходить через ту же модель с bump menu_version.

────────────────────────────────
2. СТРУКТУРА КОДА
────────────────────────────────
bot/
  index.js                — бутстрап, graceful shutdown по SIGTERM/SIGINT
  bot.js                  — создание инстанса Telegraf, общие middleware
  middleware/             — логирование, определение языка пользователя, антифлуд
  scenes/                 — сценарии (заявка на подключение, привязка группы)
  handlers/               — команды и колбэки
  worker/notifications.js — воркер очереди уведомлений
  worker/scheduler.js     — периодические задачи
  templates/              — сборка текстов сообщений (через i18n, не хардкодом)

────────────────────────────────
3. ЯЗЫК ПОЛЬЗОВАТЕЛЯ
────────────────────────────────
- Таблица telegram_users: telegram_id bigint PK, username, first_name, lang text NOT NULL DEFAULT 'ru',
  is_blocked boolean DEFAULT false, created_at, last_seen_at.
- При первом контакте определяем язык из ctx.from.language_code (uz → uz, en → en, иначе ru)
  и предлагаем подтвердить кнопками. Дальше язык берётся из таблицы.
- Все тексты бота — через существующий t(key, lang, params) и ключи bot.* во всех словарях.

────────────────────────────────
4. ВОРКЕР УВЕДОМЛЕНИЙ
────────────────────────────────
- Раз в 10 секунд забирает пачку из notifications (claimBatch с FOR UPDATE SKIP LOCKED),
  отправляет по каналу и помечает результат.
- Telegram: 403/blocked → status 'skipped' + telegram_users.is_blocked = true, без ретраев.
  429 → уважать retry_after из ответа, переносить scheduled_at. Сетевые ошибки → ретрай
  по расписанию из промта 0.1.
- Email: ошибки SMTP → ретрай. Невалидный адрес → 'failed' сразу.
- Соблюдать лимиты Telegram: не больше ~25 сообщений в секунду глобально и не больше одного
  в секунду в один чат. Сделай простой троттлер, не отправляй пачку параллельно без ограничений.
- Шаблоны сообщений рендерятся по полю template + payload. Неизвестный template — 'failed'
  с понятной ошибкой, а не падение воркера.

────────────────────────────────
5. БАЗОВЫЕ КОМАНДЫ
────────────────────────────────
- /start — приветствие, короткое описание сервиса, кнопки: «Подключить заведение»,
  «У меня уже есть аккаунт», «Задать вопрос», выбор языка.
- /help — что умеет бот.
- /lang — сменить язык.
- Владельцу сервиса (ENV OWNER_TELEGRAM_ID, поддержи список через запятую): /stats — сводка
  (заявок в очереди, заведений по статусам, ожидающих подтверждения оплат), /pending — очередь задач.
- Любое непонятное сообщение от обычного пользователя — вежливый ответ с подсказкой и, если
  написано осмысленно, пересылка владельцу как обращение в поддержку с кнопкой «Ответить».
  Ответ владельца через reply уходит пользователю от имени бота.

────────────────────────────────
6. НАДЁЖНОСТЬ И ЗАЩИТА
────────────────────────────────
- Антифлуд: не больше 20 сообщений в минуту с одного telegram_id, дальше молча игнорировать
  (не отвечать «вы флудите» — это удваивает трафик).
- Все обработчики в try/catch, ошибка в одном не роняет процесс.
- Необработанные отклонения промисов логировать и отправлять алерт владельцу с дедупликацией
  (не чаще одного одинакового алерта в 15 минут).
- Graceful shutdown: перестать забирать новые задачи, дождаться текущих, закрыть пул.
- Логи структурированные, с telegram_id, но без содержимого личных сообщений.

────────────────────────────────
EDGE CASES
────────────────────────────────
- Бот случайно запущен в двух экземплярах: polling выдаст конфликт 409 — залогируй понятно
  и заверши процесс, а не крутись в ошибках.
- BOT_TOKEN не задан — процесс сообщает об этом и завершается; веб-приложение при этом работает,
  просто уведомления копятся в очереди со статусом pending.
- Пользователь удалил чат с ботом и вернулся — is_blocked сбрасывается при новом /start.

DEFINITION OF DONE: бот стартует, отвечает на /start на трёх языках, воркер отправляет тестовое
уведомление из очереди, README дополнен разделом про запуск бота.
```

## Промт 1.2 — Заявки на подключение

```
Задача: сделать вход в воронку — заявку на подключение заведения через бота и через форму на сайте,
плюс очередь заявок в суперадминке.

────────────────────────────────
1. СХЕМА
────────────────────────────────
Таблица leads:
- id, source text CHECK (source IN ('bot','web')),
- telegram_id bigint (nullable, для web-заявок пусто), telegram_username text,
- contact_name text NOT NULL, phone text NOT NULL, email text,
- venue_name text NOT NULL, city text, venue_type text, comment text,
- status text NOT NULL DEFAULT 'new' CHECK (status IN ('new','contacted','approved','rejected','spam')),
- reject_reason text,
- venue_id integer REFERENCES venues ON DELETE SET NULL (заполняется при одобрении),
- processed_by integer REFERENCES admins, processed_at timestamptz,
- created_at timestamptz NOT NULL DEFAULT now(),
- ip_hash text, user_agent text (только для web, для антиспама).
Индексы: (status, created_at); уникальный частичный индекс на telegram_id
WHERE status IN ('new','contacted','approved') — реализует правило «один Telegram-аккаунт = одно заведение».

────────────────────────────────
2. ЗАЯВКА ЧЕРЕЗ БОТА
────────────────────────────────
Сценарий (telegraf scene), пошагово, с кнопками «Назад» и «Отмена» на каждом шаге:
1. Название заведения (2–100 символов).
2. Город или район.
3. Тип заведения кнопками: кофейня, кафе/столовая, пиццерия/суши, бар, стритфуд, кондитерская, другое.
4. Имя для связи.
5. Телефон — принимать и кнопкой «Отправить контакт» (request_contact), и вводом вручную.
   Нормализовать к формату +998XXXXXXXXX, валидировать длину и код страны.
6. Комментарий (необязательно, кнопка «Пропустить»).
7. Подтверждение: показать сводку и кнопки «Отправить» / «Исправить».

После отправки:
- Заявка создаётся, пользователю уходит подтверждение с примерным сроком ответа.
- Владельцу сервиса — уведомление с полной карточкой заявки и inline-кнопками
  «Одобрить», «Отклонить», «Написать заявителю».
- Если у telegram_id уже есть активная заявка или заведение — не создавать новую, а показать
  её статус и предложить связаться с поддержкой.

────────────────────────────────
3. ЗАЯВКА ЧЕРЕЗ ФОРМУ НА САЙТЕ
────────────────────────────────
- Роуты GET/POST /apply, отдельная страница в стилистике лендинга (тот же nav и футер).
- Поля: название заведения, город, тип, имя, телефон, email (необязательно), комментарий,
  чекбокс согласия с условиями использования (ссылка из site_settings).
- Валидация zod на сервере и мягкая подсветка на клиенте, без блокировки отправки.
- Антиспам без внешних сервисов: honeypot-поле, скрытое через CSS (не type=hidden — боты его видят),
  проверка минимального времени заполнения формы (меньше 3 секунд — отклоняем),
  rate-limit по IP (3 заявки в час), хэш IP с суточной солью, не сырой IP.
- После успеха — страница «спасибо» с кнопкой «Перейти в бота», чтобы человек всё равно
  оказался в Telegram, где с ним удобнее работать.
- Уведомление владельцу в бота + дублирование на email из site_settings.

────────────────────────────────
4. ОЧЕРЕДЬ ЗАЯВОК В СУПЕРАДМИНКЕ
────────────────────────────────
- Страница /superadmin/leads: таблица с фильтрами по статусу и поиском по названию и телефону,
  сортировка по дате, пагинация по 25.
- Карточка заявки: все поля, история статусов, кнопки «Связался», «Одобрить», «Отклонить», «Спам».
- «Одобрить» открывает форму создания заведения, предзаполненную данными из заявки:
  slug (сгенерировать транслитерацией из названия, проверить уникальность, при конфликте
  добавлять -2, -3), название, телефон, язык по умолчанию, логин администратора.
  При сохранении создаётся venue в статусе draft и venue_admin с одноразовым паролем.
- «Отклонить» требует причину, она уходит заявителю в бота или на email.
- Все действия логируются через logAction, entity_type 'lead' (расширь CHECK-ограничение миграцией).
- Пункт «Заявки» в admin-sidebar для роли superadmin, с бейджем количества новых.

────────────────────────────────
EDGE CASES
────────────────────────────────
- Один и тот же телефон в двух заявках с разных Telegram-аккаунтов — не блокируем, но показываем
  владельцу предупреждение «похожая заявка уже есть» со ссылкой.
- Заявка одобрена, а заведение потом удалено — lead.venue_id обнуляется, статус меняется
  на 'rejected' с системной причиной.
- Пользователь начал сценарий в боте и бросил на середине — незавершённые сцены не создают записей
  и очищаются через 30 минут неактивности.
- Пользователь отправил заявку через сайт, потом пришёл в бота: при вводе того же телефона
  предложить привязать существующую заявку, а не создавать вторую.

DEFINITION OF DONE: заявка проходит и от бота, и от формы, появляется в суперадминке,
одобрение создаёт заведение в статусе draft.
```

## Промт 1.3 — Жизненный цикл заведения и подписки

```
Задача: ввести явный жизненный цикл заведения и автоматику вокруг подписки. Сейчас есть только
поле subscription_until без какой-либо логики.

────────────────────────────────
1. СТАТУСЫ
────────────────────────────────
Миграция: venues.status text NOT NULL DEFAULT 'active'
CHECK (status IN ('draft','trial','active','grace','suspended','archived'))
Плюс поля: published_at timestamptz, trial_started_at timestamptz, trial_ends_on date,
suspended_at timestamptz, archived_at timestamptz, status_changed_at timestamptz NOT NULL DEFAULT now().
Существующим заведениям при миграции проставить 'active' и published_at = created_at,
чтобы ничего не сломалось.

Смысл статусов:
- draft — создано, но не опубликовано. Публичная страница отдаёт 404. Админка полностью работает,
  чтобы владелец успел заполнить меню до старта триала.
- trial — опубликовано, идут 30 бесплатных дней. Всё работает.
- active — оплаченный период. Всё работает.
- grace — оплата просрочена, но 5 дней меню продолжает работать. В админке заметный баннер.
- suspended — меню заменено на страницу-заглушку. Данные целы, админка доступна только для
  просмотра и оплаты, редактирование заблокировано.
- archived — через 90 дней в suspended. Публичная страница 410 Gone, данные помечены к удалению,
  фото не удаляются автоматически (только вручную владельцем сервиса).

────────────────────────────────
2. ПУБЛИКАЦИЯ И СТАРТ ТРИАЛА
────────────────────────────────
- Кнопка «Опубликовать меню» на дашборде админки заведения, доступна только в статусе draft.
- Перед публикацией — проверка готовности: минимум одна категория, минимум 3 позиции,
  заполнены название и телефон. Если чего-то нет — показать чеклист со ссылками на нужные экраны.
- В момент публикации: status = 'trial', published_at = now(), trial_started_at = now(),
  trial_ends_on = now + 30 дней, subscription_until = trial_ends_on.
- Триал даётся ОДИН РАЗ. Поле trial_started_at не обнуляется никогда; повторная публикация
  после suspended не даёт нового бесплатного периода. Проверяй это явно.
- Владельцу сервиса — уведомление о публикации нового заведения.

────────────────────────────────
3. ЕЖЕЧАСНАЯ ЗАДАЧА ПЕРЕСЧЁТА
────────────────────────────────
В bot/worker/scheduler.js, запуск раз в час (не раз в сутки — так проще пережить перезапуск),
но с идемпотентностью: каждое действие выполняется не чаще одного раза в сутки на заведение.
Логика по каждому заведению:
- subscription_until >= сегодня → active (или trial, если триал ещё идёт);
- subscription_until < сегодня и прошло <= 5 дней → grace;
- прошло > 5 дней → suspended, suspended_at = now();
- в suspended > 90 дней → archived, с уведомлением за 7 дней до архивации.
Все переходы писать в таблицу venue_status_history (venue_id, from_status, to_status, reason,
created_at, actor: 'system' или admin_id) — это спасёт при разборе спорных ситуаций.

────────────────────────────────
4. НАПОМИНАНИЯ
────────────────────────────────
Ставить в очередь notifications с dedup_key, чтобы не задваивались:
- за 7 дней до окончания — мягкое напоминание;
- за 3 дня — напоминание с реквизитами и кнопкой «Я оплатил»;
- за 1 день — последнее предупреждение;
- в день истечения — «меню продолжит работать ещё 5 дней»;
- на 3-й день grace — предупреждение о скором отключении;
- в момент suspended — уведомление владельцу заведения и владельцу сервиса;
- за 7 дней до архивации.
Канал: Telegram, если заведение привязано к боту; иначе email; если нет ни того ни другого —
задача владельцу сервиса «связаться вручную».
Не слать напоминания заведениям в статусах draft и archived.

────────────────────────────────
5. ПОВЕДЕНИЕ ПУБЛИЧНОЙ СТРАНИЦЫ
────────────────────────────────
Критично: QR-коды уже напечатаны и висят на столах. Страница не должна становиться мёртвой.
- draft — 404 (страницы ещё не существовало, ссылок на неё нет).
- trial / active / grace — обычное меню.
- suspended — специальная страница: логотип и название заведения, телефон, адрес, соцсети,
  вежливый текст «меню временно недоступно». HTTP 200, чтобы не портить индексацию.
  Никакого упоминания неоплаты — гость не должен знать о финансовых отношениях.
- archived — 410 Gone с той же вёрсткой.
- is_active = false (ручное отключение суперадмином) работает поверх любого статуса и даёт
  ту же страницу, что suspended.

────────────────────────────────
6. ОГРАНИЧЕНИЯ В АДМИНКЕ
────────────────────────────────
- grace: всё работает, вверху предупреждающий баннер с датой отключения и кнопкой оплаты.
- suspended: доступны только дашборд и раздел «Подписка». Попытка открыть категории или позиции —
  редирект на «Подписка» с объяснением. Проверку делать в middleware, а не в шаблонах.
- archived: только чтение и кнопка «Написать в поддержку».

────────────────────────────────
EDGE CASES
────────────────────────────────
- Часовые пояса: все даты подписки — date, сравнение в UTC. В проекте уже есть src/utils/dateOnly.js —
  используй его, не добавляй новой логики дат.
- Суперадмин продлил подписку заведению в suspended — статус должен немедленно вернуться в active,
  страница ожить, кэш сброситься. Проверь этот сценарий явно.
- Заведение опубликовано и в тот же день переведено в suspended вручную — триал не сгорает,
  trial_ends_on сохраняется.
- Перезапуск процесса посреди пересчёта не должен приводить к двойным уведомлениям — за это
  отвечает dedup_key.

DEFINITION OF DONE: все шесть статусов достижимы, страница-заглушка выглядит как часть сервиса,
напоминания уходят по одному разу, история переходов пишется.
```

## Промт 1.4 — Раздел «Подписка» и ручное подтверждение оплаты

```
Задача: сделать полуавтоматическую оплату. Деньги приходят переводом на карту вручную, всё
остальное автоматизировано. Модуль должен быть готов к замене реквизитов на Click или Payme
без переписывания логики.

────────────────────────────────
1. СХЕМА
────────────────────────────────
Таблица payment_claims (заявка на оплату от заведения):
- id, venue_id NOT NULL REFERENCES venues ON DELETE CASCADE,
- months integer NOT NULL CHECK (months IN (1,3,6,12)),
- amount numeric(12,2) NOT NULL, currency text NOT NULL DEFAULT 'UZS',
- method text NOT NULL DEFAULT 'card_transfer',
- payer_note text, receipt_url text (скриншот чека, необязательно),
- status text NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','approved','rejected','cancelled')),
- reviewed_by integer REFERENCES admins, reviewed_at timestamptz, reject_reason text,
- payment_id integer REFERENCES payments (создаётся при одобрении),
- created_at timestamptz NOT NULL DEFAULT now().
Частичный уникальный индекс: одна pending-заявка на заведение (UNIQUE (venue_id) WHERE status = 'pending').

Реквизиты хранить в site_settings, новыми полями: payment_card_number, payment_card_holder,
payment_bank_name, payment_instructions_ru/uz/en. Не в коде и не в ENV — владелец должен менять
их из суперадминки без деплоя.

Цены: месячная цена уже есть в src/config/constants.js. Добавь туда же множители для периодов
(3, 6, 12 месяцев) со скидкой и функцию расчёта итоговой суммы. Не хардкодь суммы в шаблонах —
считай из констант, чтобы правка цены была в одном месте.

────────────────────────────────
2. ЭКРАН «ПОДПИСКА» В АДМИНКЕ ЗАВЕДЕНИЯ
────────────────────────────────
Роут /admin/subscription, пункт в сайдбаре (подойдёт иконка clock или star).
Содержание:
- Крупный блок статуса: статус словами, дата окончания, сколько дней осталось.
  Для trial — «бесплатный период, осталось N дней».
- Выбор периода: 1 / 3 / 6 / 12 месяцев карточками с ценой за период и подписью выгоды

## Промт 1.5 — Доступы: пароли, восстановление, привязка Telegram

```
Задача: закрыть всё, что связано с доступом в админку, — выдача пароля при создании, смена,
восстановление через почту и через бота, привязка Telegram-аккаунта владельца.

────────────────────────────────
1. ПЕРВИЧНЫЙ ПАРОЛЬ
────────────────────────────────
- При одобрении заявки генерируется одноразовый пароль (12 символов, без похожих символов
  0/O/l/1/I, чтобы можно было продиктовать по телефону) и сохраняется хэшем.

  Логин и пароль отправлять ДВУМЯ сообщениями: логин и ссылку на вход первым, пароль вторым.
  Дешёвая, но реальная защита при пересылке скриншотов.
- При первом входе с must_change_password = true пользователя принудительно ведёт на форму смены
  пароля, минуя остальную админку (middleware, а не проверка в шаблоне).

────────────────────────────────
2. СМЕНА ПАРОЛЯ
────────────────────────────────
- Раздел в /admin/venue-settings или отдельная страница /admin/password.
- Требуется текущий пароль. Новый — минимум 8 символов, проверка на совпадение с логином
  и на вхождение в короткий список самых частых паролей (положи список в src/utils/, 200 строк хватит).
- Индикатор надёжности на клиенте — подсказка, без блокировки отправки.
- После смены — инвалидация всех остальных сессий этого администратора (connect-pg-simple хранит
  сессии в таблице; удали строки этого пользователя, кроме текущей).
- Уведомление на почту и в Telegram: «пароль изменён, если это не вы — напишите нам».

────────────────────────────────
3. ВОССТАНОВЛЕНИЕ ПО EMAIL
────────────────────────────────
Таблица password_reset_tokens: id, admin_id, token_hash text NOT NULL, expires_at timestamptz,
used_at timestamptz, requested_ip_hash text, created_at.
- Роут /admin/forgot: одно поле «email или логин».
- Ответ ВСЕГДА одинаковый, независимо от того, найден пользователь или нет:

  проверить, какие логины существуют.
- Токен: 32 случайных байта, в БД хранится только SHA-256 хэш, в письме — сырое значение.

  помечаются использованными.
- Rate-limit: 3 запроса на аккаунт в час, 10 с одного IP в час.
- Ссылка вида APP_BASE_URL/admin/reset?token=... Страница проверяет токен до показа формы.
- После успешной смены — все токены погашены, все сессии инвалидированы, уведомление отправлено.
- Для восстановления нужен email у администратора: добавь admins.email (nullable, unique)
  и поле в форму создания заведения в суперадминке. Если email не задан — сообщение

────────────────────────────────
4. ПРИВЯЗКА TELEGRAM К АККАУНТУ ЗАВЕДЕНИЯ
────────────────────────────────
Нужна для уведомлений и для восстановления доступа без почты.
- В админке кнопка «Привязать Telegram» показывает 6-значный код и ссылку на бота

- Таблица venue_telegram_links: venue_id, admin_id, code, expires_at (15 минут), used_at.
  Код одноразовый, регистронезависимый, из символов без 0/O/1/I.
- Бот по deep-link принимает код, проверяет срок и одноразовость, привязывает telegram_id
  к admins.telegram_id и venues.owner_telegram_id.
- Восстановление через бота: команда «Забыл пароль» доступна только привязанному аккаунту,

- Отвязка из админки, с подтверждением.

────────────────────────────────
5. ЗАЩИТА ВХОДА
────────────────────────────────
- Rate-limit на /admin/login: 10 попыток с IP за 15 минут, 5 попыток на конкретный логин за 15 минут.
- После 5 неудачных попыток на аккаунт — задержка ответа 2 секунды. Реализуй так, чтобы это
  не блокировало event loop.
- Ошибка входа всегда одинаковая: «неверный логин или пароль», без уточнения, что именно не так.
- Логировать неудачные входы в admin_action_logs с типом 'auth_fail' и хэшем IP.
- Уведомление владельцу заведения при 10 неудачных попытках подряд.

────────────────────────────────
EDGE CASES
────────────────────────────────
- Токен восстановления использован дважды одновременно — транзакция с проверкой used_at.
- Администратор удалён, а токен ещё жив — токен не работает, ошибка нейтральная.
- Email указан у двух администраторов — запрещай на уровне unique-индекса.
- Пользователь привязал Telegram, потом сменил аккаунт — новая привязка перетирает старую,

DEFINITION OF DONE: полный цикл восстановления работает и по почте, и через бота; принудительная

## Промт 2.1 — Модификаторы, размеры и добавки

```
Задача: позиция меню может иметь варианты (размер, объём) и дополнения (сироп, соус, топпинг).
Сейчас у позиции ровно одна цена, для кофеен этого не хватает.

────────────────────────────────
1. СХЕМА
────────────────────────────────
Таблица item_option_groups (группа выбора у позиции):
- id, item_id NOT NULL REFERENCES items ON DELETE CASCADE,
- name_ru/name_uz/name_en text (name_ru NOT NULL),
- selection text NOT NULL CHECK (selection IN ('single','multiple')),
- is_required boolean NOT NULL DEFAULT false,
- min_select integer NOT NULL DEFAULT 0, max_select integer,
- sort_order integer NOT NULL DEFAULT 0.
CHECK: min_select >= 0; max_select IS NULL OR max_select >= min_select;
для selection = 'single' max_select = 1 и min_select <= 1.

Таблица item_options (вариант внутри группы):
- id, group_id NOT NULL REFERENCES item_option_groups ON DELETE CASCADE,
- name_ru/name_uz/name_en, price_delta numeric(12,2) NOT NULL DEFAULT 0,
- is_available boolean NOT NULL DEFAULT true,
- is_default boolean NOT NULL DEFAULT false,
- sort_order integer NOT NULL DEFAULT 0.
CHECK: price_delta >= 0. Только надбавка, не скидка — иначе легко получить отрицательную цену.
Если нужна «маленькая порция дешевле», базовой ценой делается маленькая.

Индексы на item_id и group_id. Ограничения: не больше 5 групп на позицию и 20 вариантов в группе —
проверяй в валидаторе, а не только в БД, иначе сообщение об ошибке будет нечитаемым.

────────────────────────────────
2. АДМИНКА
────────────────────────────────
- Редактирование групп и вариантов внутри формы позиции, не отдельной страницей.
- Добавление группы: название, тип выбора (один / несколько), обязательность, лимиты.
- Варианты списком с сортировкой перетаскиванием (HTML5 drag & drop или простая реализация
  на pointer events, без библиотек). ОБЯЗАТЕЛЬНО продублируй кнопками «вверх / вниз» —
  для тач-устройств и доступности.
- Надбавка вводится в сумах, целыми числами. Ноль допустим и означает «без доплаты».
- Кнопка «Скопировать группу из другой позиции» — частый сценарий «сироп есть у всех кофе».
  Плюс кнопка «Применить эту группу к нескольким позициям» с выбором позиций чекбоксами.
- Предпросмотр рядом: как это увидит гость, с пересчётом итоговой цены.

────────────────────────────────
3. ПУБЛИЧНАЯ СТРАНИЦА
────────────────────────────────
- В строке позиции подпись мелким шрифтом «2 размера · 3 добавки» (счётчики групп по типу).
  Если групп нет — подписи нет.
- Цена: если есть группа с надбавками, показывать «от <базовая цена>».
- Кнопка «+» у позиции с группами открывает модалку выбора, а не добавляет сразу.
- Модалка: фото сверху, название, описание, затем группы. Обязательные группы помечены,
  кнопка «Добавить» неактивна, пока не выбрано необходимое. Итоговая цена пересчитывается на лету
  и показана на кнопке.
- Одиночный выбор — радиокнопки, множественный — чекбоксы. Использовать нативные input
  с кастомизацией через CSS, а не div с обработчиками: это бесплатно даёт доступность
  и работу с клавиатуры.
- Недоступные варианты (is_available = false) показываются приглушёнными и не выбираются.
- На мобильном модалка — bottom sheet, выезжающий снизу, закрывается свайпом вниз и кликом

## Промт 2.5 — PWA и офлайн

```

обычная ситуация.

────────────────────────────────
1. MANIFEST
────────────────────────────────
- Динамический манифест на заведение: /menu/:slug/manifest.webmanifest.
- name и short_name из названия заведения, start_url на меню с меткой источника,
  display 'standalone', theme_color и background_color из существующих токенов дизайн-системы
  (значениями, потому что в манифесте переменные не работают).
- Иконки: генерировать из логотипа заведения через sharp в размерах 192, 512 и maskable 512
  при загрузке логотипа, класть рядом с остальными файлами заведения. Если логотипа нет —
  использовать иконку сервиса.
- Манифест кэшировать и инвалидировать вместе с меню.

────────────────────────────────
2. SERVICE WORKER
────────────────────────────────
- Один файл /sw.js в корне, регистрируется только на страницах меню.
- Стратегии:
  * HTML меню — network-first с таймаутом 3 секунды, при неудаче отдаём кэш;
  * CSS, JS, шрифты — cache-first с фоновой ревалидацией;

    вытеснение по LRU. Считать размер через Cache API, не хранить неограниченно;
  * всё остальное — сеть без кэша.
- Версия кэша завязана на menu_version заведения: при изменении меню старый кэш HTML сбрасывается.
  Передавать версию в sw через URL регистрации или postMessage при загрузке страницы.
- Офлайн-фолбэк: если нет ни сети, ни кэша — аккуратная страница «нет соединения» в стилистике
  сервиса, с кнопкой «Повторить».
- Никаких попыток кэшировать POST-запросы, корзину или заказы.

────────────────────────────────
3. ИНДИКАЦИЯ
────────────────────────────────
- Если страница отдана из кэша и сеть недоступна — ненавязчивая полоса «показано сохранённое меню,
  цены могли измениться». Не модалка, а полоса, которую можно закрыть.
- При восстановлении сети полоса исчезает, содержимое молча обновляется, если версия изменилась.
- Предложение «установить приложение» показывать не сразу: только при втором визите и только если
  гость провёл на странице больше 20 секунд. Одно предложение на 30 дней, отказ запоминается.

────────────────────────────────
EDGE CASES
────────────────────────────────
- Обновление service worker не должно требовать двойной перезагрузки: используй skipWaiting
  и clients.claim, но сначала уведоми открытые вкладки.
- Гость установил PWA, заведение перешло в suspended — при открытии показывается страница-заглушка,

- Приватный режим браузера, Cache API недоступен — регистрация в try/catch, страница работает
  как обычно.
- iOS Safari имеет ограничения на PWA: проверь, что базовый сценарий (открытие, кэш статики)
  работает, и не полагайся на beforeinstallprompt, которого там нет.

DEFINITION OF DONE: меню открывается в офлайне после первого визита, обновление меню приводит
к обновлению кэша, установка предлагается ненавязчиво.

## Промт 3.1 — Импорт меню из Excel и массовые операции

```
Задача: убрать главный барьер онбординга — ручной ввод 80 позиций. Это же снимет нагрузку
с владельца сервиса, который сейчас заносит меню за клиентов.

────────────────────────────────
1. ИМПОРТ
────────────────────────────────
- Зависимость: xlsx (SheetJS). Поддержать .xlsx, .xls и .csv с автоопределением разделителя

────────────────────────────────
2. ПРЕДПРОСМОТР И ВАЛИДАЦИЯ
────────────────────────────────
Ключевой экран. Таблица с результатом разбора и пометкой по каждой строке:
- «Новая» — позиции с таким названием в этой категории нет;
- «Обновление» — есть, будут изменены такие-то поля (показать какие именно, старое → новое);
- «Без изменений» — совпадает полностью, будет пропущена;
- «Ошибка» — с конкретной причиной в строке.
Сверху сводка: N новых, N обновлений, N ошибок. Кнопка «Применить» неактивна при наличии ошибок,
но есть отдельная кнопка «Применить, пропустив строки с ошибками».

Правила валидации:
- Цена: принимать «25 000», «25000», «25 000 сум», «25.000» — нормализовать. Отрицательная
  или нечисловая → ошибка.
- Название пустое → ошибка. Длиннее 200 символов → ошибка с указанием строки.
- Категории, которых нет, создаются автоматически — но покажи это отдельным списком

- Теги: принимать через запятую, сопоставлять с допустимым списком без учёта регистра,
  неизвестные — предупреждение, а не ошибка.
- Дубликаты внутри файла — предупреждение, применяется последняя строка.

────────────────────────────────
3. ПРИМЕНЕНИЕ
────────────────────────────────
- Всё в одной транзакции. Частично применённый импорт недопустим.
- Лимиты: 2000 строк, файл до 10 МБ. Больше — понятная ошибка с предложением разбить.
- Импорт НЕ удаляет позиции, которых нет в файле. Удаление — только явное действие отдельной
  кнопкой с подтверждением и списком того, что удалится.
- После применения — bump menu_version, инвалидация кэша, запись в logAction с количествами.
- Отчёт: сколько создано, обновлено, пропущено, со ссылкой «посмотреть импортированные».
- Сам файл импорта сохранять в uploads на 30 дней — чтобы можно было разобраться, если владелец
  скажет «оно всё испортило».

────────────────────────────────
4. МАССОВЫЕ ОПЕРАЦИИ
────────────────────────────────
На странице позиций — чекбоксы и панель действий, появляющаяся при выборе:
- Изменить цену: на +N%, −N%, +N сум или установить значение. ОБЯЗАТЕЛЬНО предпросмотр
  «было → станет» до применения, с округлением до 100 сум (настраиваемо).
- Перенести в другую категорию.
- Включить или выключить доступность.
- Проставить или снять тег.
- Удалить (с подтверждением и указанием количества).
- Экспорт выбранных в Excel — в том же формате, что и импорт, чтобы цикл был замкнутым.
Все массовые операции — в транзакции, с ОДНОЙ записью в логе, а не N записями.

────────────────────────────────
EDGE CASES
────────────────────────────────
- Файл с одной строкой заголовков и без данных — понятное сообщение, а не пустой предпросмотр.
- Объединённые ячейки в Excel: SheetJS отдаёт их как пустые. Предупреди в шаблоне, что объединять
  нельзя, и обработай пустое значение категории как «взять из предыдущей строки» — это частый

- Файл с несколькими листами — дать выбрать лист.
- Загрузка двух импортов одновременно из двух вкладок — блокировка на уровне заведения на время
  применения.
- Импорт в заведение в статусе suspended запрещён.
- Цены в других валютах в файле — не пытайся конвертировать, выдай ошибку.

DEFINITION OF DONE: меню из 100 строк заливается за одну попытку, предпросмотр честно показывает
изменения, ошибочный файл не портит существующие данные.

## Промт 3.2 — Аналитика

```
Задача: заменить единственный счётчик просмотров на аналитику, из которой владелец заведения
делает выводы. Сейчас есть только venue_page_views с суточным счётчиком.

────────────────────────────────
1. СБОР СОБЫТИЙ
────────────────────────────────
Таблица menu_events (сырые события, живут 180 дней):

- Запись событий не должна замедлять ответ: вставка асинхронная, ошибки логируются, но
  не возвращаются клиенту.

────────────────────────────────
2. АГРЕГАЦИЯ
────────────────────────────────
- Таблица menu_stats_daily: venue_id, stat_on date, metric text, dimension text, value numeric,

- Ежечасная задача агрегирует вчерашние и сегодняшние события. Идемпотентно: пересчёт того же дня

- Сырые события старше 180 дней удаляются пачками, агрегаты хранятся бессрочно.
- Существующую venue_page_views оставить и наполнять из агрегатов, чтобы не сломать текущий дашборд,

────────────────────────────────
3. ЭКРАН АНАЛИТИКИ
────────────────────────────────
Страница /admin/analytics с выбором периода (7 дней, 30 дней, произвольный). Блоки:
- Просмотры меню: график по дням, сравнение с предыдущим периодом в процентах.
- Часы пик: столбчатая диаграмма по часам суток, усреднённая за период. Владелец увидит,
  когда ставить людей в смену.
- Дни недели: столбцы по дням.
- Топ-10 просматриваемых позиций и топ-10 добавляемых в корзину — двумя списками рядом.
- Отдельный блок «Смотрят, но не берут»: высокий просмотр при низком добавлении. Это блюда,
  которые привлекают внимание, но отталкивают ценой или описанием.
- Позиции, которые не просматривали ни разу за период — кандидаты на удаление из меню.
- Поисковые запросы: топ запросов и ОТДЕЛЬНО топ запросов без результата. Второе — самое ценное:

────────────────────────────────

────────────────────────────────
- Экспорт периода в Excel одной кнопкой.

────────────────────────────────

────────────────────────────────
- Мало данных (меньше 20 событий за период) — не рисовать графики, показать «данных пока мало».

DEFINITION OF DONE: экран открывается быстро на данных за 30 дней, пустые поисковые запросы видны,

## Промт 3.3 — Сбор отзывов с уходом в Google и Яндекс

```
Задача: превращать довольных гостей в отзывы на картах, а недовольных — в обратную связь владельцу.
Это то, за что заведения готовы платить отдельно.

────────────────────────────────
1. СХЕМА
────────────────────────────────
Миграция для venues:
- google_review_url text, yandex_review_url text — прямые ссылки на форму отзыва;
- reviews_enabled boolean NOT NULL DEFAULT false;
- reviews_prompt_delay_sec integer NOT NULL DEFAULT 45;
- reviews_threshold smallint NOT NULL DEFAULT 4 CHECK (BETWEEN 1 AND 5).
Существующее поле address_2gis_url НЕ трогаем — оно остаётся ссылкой «как доехать»
и к отзывам отношения не имеет.

Таблица reviews:
- id, venue_id NOT NULL, rating smallint NOT NULL CHECK (BETWEEN 1 AND 5),
- comment text, contact text (телефон или Telegram, необязательно),
- table_id integer, lang text, session_hash text,
- went_external boolean NOT NULL DEFAULT false (нажал ли гость кнопку перехода на карты),
- external_target text CHECK (external_target IN ('google','yandex')),
- status text NOT NULL DEFAULT 'new' CHECK (status IN ('new','read','resolved','spam')),
- owner_reply text, replied_at timestamptz,
- created_at timestamptz NOT NULL DEFAULT now().
Индексы: (venue_id, created_at), (venue_id, status).

────────────────────────────────
2. ПОТОК ДЛЯ ГОСТЯ (мягкая схема)
────────────────────────────────
Шаг 1. Приглашение ненавязчивой карточкой внизу страницы:
- не раньше, чем через reviews_prompt_delay_sec на странице,
- или сразу после отправки заказа,
- не чаще одного раза в 30 дней на session_hash (localStorage плюс проверка на сервере),
- никогда, если гость уже оставлял отзыв.
Текст нейтральный: «Как вам у нас?» и пять звёзд. Никаких «поставьте пять звёзд».

Шаг 2. Гость выбирает оценку. Дальше две ветки, но обе кнопки видны всем:
- Оценка >= порога: экран благодарности, крупно две кнопки «Отзыв в Google» и «Отзыв в Яндексе»
  (только те, для которых заполнены ссылки), плюс необязательное поле «что понравилось» для владельца.
- Оценка < порога: сначала поле «расскажите, что пошло не так — это увидит только владелец»
  и кнопка отправки. ПОД ней, менее акцентно, но обязательно видимо, те же кнопки публичного отзыва.
  Не прятать их и не блокировать: гость имеет право написать публично, и скрывать эту возможность
  неэтично и рискованно с точки зрения правил площадок.

Шаг 3. После отправки — благодарность. Если гость оставил контакт, добавить «владелец может
связаться с вами».

Звёзды делать нативными radio-инпутами с CSS-кастомизацией: работает с клавиатуры, читается
скринридером, не требует JS для базового сценария.

────────────────────────────────
3. РЕЙТИНГ В КАРТОЧКЕ ЗАВЕДЕНИЯ
────────────────────────────────
- Если reviews_enabled и внутренних отзывов >= 5 — показывается средняя из внутренних оценок

- Иначе — ручное значение, как раньше.
- НИКОГДА не складывать и не смешивать эти два источника.
- В суперадминке рядом с полями ручного рейтинга — пояснение, когда они используются, и текущее
  фактическое значение.
- Формулировка под звёздами должна быть честной: «оценки гостей в меню», а не «отзывы», чтобы

────────────────────────────────
4. АДМИНКА ЗАВЕДЕНИЯ
────────────────────────────────
- Раздел /admin/reviews: список отзывов, фильтр по оценке и статусу, бейдж непрочитанных в сайдбаре.
- Карточка отзыва: оценка, текст, дата, стол, язык, контакт, ушёл ли гость на карты.
- Действия: «прочитано», «решено», «спам», поле заметки для себя.
- Если гость оставил контакт — кнопки «Позвонить» и «Написать в Telegram».
- Настройки: включение сбора, ссылки на Google и Яндекс с ПОШАГОВОЙ инструкцией, где их взять
  (найти ссылку на форму отзыва неочевидно), задержка, порог, предпросмотр того, что увидит гость.
- Уведомление в Telegram владельцу заведения при отзыве ниже порога — немедленно.
  При высокой оценке не спамить, включать в еженедельную сводку.

────────────────────────────────
EDGE CASES
────────────────────────────────
- Ссылки на карты не заполнены — блок благодарности показывает только поле для владельца,
  без пустых кнопок.
- Накрутка: один session_hash — один отзыв в 30 дней; лимит 20 отзывов с одного IP в сутки
  (заведение с общим Wi-Fi); отзывы без текста и с одинаковым текстом подряд помечать

- Заведение только подключилось, отзывов 0 — карточка не показывает «0.0», блок рейтинга скрыт.
- Отзыв оставлен, потом заведение выключило сбор — данные остаются, рейтинг возвращается к ручному.
- Очень длинный комментарий — ограничить 2000 символов на сервере.
- Не показывать приглашение к отзыву на странице заведения в статусе suspended.

DEFINITION OF DONE: полный поток от звезды до перехода на Google работает, низкая оценка доходит
до владельца в Telegram мгновенно, рейтинг в карточке считается по согласованному правилу.

## Промт 3.4 — Печатные материалы: QR-макеты в PDF

```
Задача: сейчас есть только qr.png 480px. Нужны готовые к печати материалы, которые владелец
скачивает и несёт в типографию или печатает сам.

────────────────────────────────
1. ТЕХНИЧЕСКАЯ ОСНОВА
────────────────────────────────
- Зависимость: pdfkit. Никаких headless-браузеров — это лишние сотни мегабайт и точка отказа.
- Шрифты: pdfkit требует TTF или OTF. Добавь в src/public/fonts TTF-версии Playfair Display
  и Manrope (только нужные начертания, чтобы не раздувать репозиторий) и подключай их в PDF.
  Проверь, что кириллица и латиница с диакритикой рендерятся корректно.
- QR генерировать через существующий qrcode в SVG и вставлять векторно, а не растром — тогда
  качество не зависит от размера печати.
- Уровень коррекции ошибок QR: 'M' по умолчанию, 'H' для макетов с логотипом в центре.

────────────────────────────────
2. МАКЕТЫ
────────────────────────────────
Все в фирменной стилистике, с теми же цветами и шрифтами, что в вебе.

2. Наклейка круглая 80 мм: QR и минимум текста.
3. Наклейка прямоугольная 90x50 мм (размер визитки): QR слева, название и призыв справа.
4. Лист A4 на дверь или стену: крупный QR, название, призыв, контакты и часы работы.
5. Лист A4 с сеткой наклеек: 12 одинаковых QR под резку, с метками реза.
6. Лист «QR по столам»: сетка макетов, где у каждого свой QR с токеном стола и подписанным номером.
   Самый востребованный вариант, если включены заказы.

────────────────────────────────
3. НАСТРОЙКИ ПЕРЕД СКАЧИВАНИЕМ
────────────────────────────────
Экран /admin/print:
- Выбор макета карточками с миниатюрой.
- Языки призыва: чекбоксы из включённых у заведения. Если выбрано два — текст в две строки.

4. КАЧЕСТВО ПЕЧАТИ
────────────────────────────────
- Вылеты 3 мм и метки реза на макетах для типографии.
- Минимальный физический размер QR — 25 мм, иначе телефоны с плохими камерами не читают.
  Не позволяй настройкам сделать меньше.
- Тихая зона вокруг QR не меньше 4 модулей — заложи в макет и не давай тексту в неё заезжать.
- Контраст QR: тёмный на светлом, всегда. Не выворачивать.
- Проверь сканируемость всех макетов на реальном телефоне и опиши это в отчёте.

────────────────────────────────
EDGE CASES
────────────────────────────────
- Очень длинное название заведения: автоматически уменьшать кегль до предела, дальше переносить
  на две строки, дальше обрезать многоточием. Макет не должен разъезжаться.
- Нет логотипа — макет перестраивается без пустого места.
- Slug содержит символы, требующие экранирования в URL — проверь корректность закодированной ссылки.
- Генерация PDF на 100 столов не должна блокировать процесс: делай потоково (pdfkit это умеет)

- Заведение в draft — печатать можно, но с предупреждением «меню ещё не опубликовано,
  QR пока не работает».

DEFINITION OF DONE: шесть макетов скачиваются, кириллица не ломается, QR со стола сканируется
и открывает меню с нужным столом.

```
Задача: сейчас admins.venue_id — один администратор к одному заведению. Для сетей из двух-трёх

## Промт 3.7 — Свой домен для заведения

```
Задача: menu.mykafe.uz вместо qr.menu/menu/slug. На выделенном сервере это реально; нужна
маршрутизация по хосту и автовыпуск сертификатов.

────────────────────────────────
1. СХЕМА
────────────────────────────────
Таблица venue_domains:
- id, venue_id NOT NULL REFERENCES venues ON DELETE CASCADE,
- domain text NOT NULL UNIQUE (нижний регистр, без протокола и слэшей, с валидацией),
- status text NOT NULL DEFAULT 'pending'
  CHECK (status IN ('pending','verifying','active','failed','disabled')),
- verification_token text NOT NULL, verified_at timestamptz, last_check_at timestamptz,
- last_error text, is_primary boolean NOT NULL DEFAULT true, created_at.
Ограничение: не больше 2 доменов на заведение (основной и алиас с www).

────────────────────────────────
2. МАРШРУТИЗАЦИЯ ПО ХОСТУ
────────────────────────────────
- Middleware в начале цепочки: если Host не совпадает с основным доменом сервиса, ищем домен
  в venue_domains со status = 'active' и подменяем маршрут на публичное меню этого заведения.
  Результат поиска кэшировать в памяти с инвалидацией через тот же NOTIFY.
- На кастомном домене доступно ТОЛЬКО публичное меню. Админка, лендинг и суперадминка — редирект
  на основной домен. Это и безопаснее, и правильнее для сессий.
- Cookie сессии не должны выставляться на кастомных доменах.
- Канонический URL, hreflang, OG и sitemap на кастомном домене указывают на него же, а не на
  основной домен, иначе поисковики склеят страницы неправильно.
- Редирект с www на без-www (или наоборот, по настройке) — 301.

────────────────────────────────
3. ПРОВЕРКА ВЛАДЕНИЯ И СЕРТИФИКАТЫ
────────────────────────────────
- В админке инструкция «добавьте CNAME на <основной домен>» либо A-запись на IP сервера, плюс
  TXT-запись с verification_token для подтверждения владения.
- Периодическая проверка DNS из планировщика (dns.promises.resolve), не чаще раза в 5 минут
  на домен, с экспоненциальным отступом при неудачах и остановкой через 48 часов с переводом в 'failed'.
- Сертификаты: nginx + certbot с HTTP-01. Реализовать так:
  * nginx проксирует /.well-known/acme-challenge/ на приложение или на общий каталог;
  * при переходе домена в 'verifying' приложение кладёт задачу на выпуск;
  * выпуск выполняет отдельный скрипт (scripts/issue-cert.sh), вызываемый по задаче, а не напрямую
    из Node — так проще отлаживать и не нужны root-права у приложения;
  * после успешного выпуска домен переходит в 'active', владельцу уходит уведомление.
- Автопродление — стандартным таймером certbot, с алертом владельцу сервиса при неудаче.
- Подробно опиши требуемую конфигурацию nginx в README, включая обработку неизвестных хостов
  (отдавать 421 или редирект на основной домен, но НЕ чужое меню).

────────────────────────────────
4. АДМИНКА
────────────────────────────────
- Раздел «Свой домен» в настройках заведения: ввод домена, статус с понятным объяснением на каждом
  шаге, кнопка «Проверить сейчас» (лимит 1 раз в минуту), кнопка «Отключить».
- Каждый статус объясняется человеческим языком: что сделано, что осталось, сколько обычно занимает.
  «pending» без объяснения — гарантированный вопрос в поддержку.
- Если DNS настроен неверно — показать, что именно видно сейчас и что ожидается.

────────────────────────────────
EDGE CASES
────────────────────────────────
- Домен указан на сервис, но заведение в suspended — показывается страница-заглушка, сертификат
  продолжает продлеваться.
- Заведение удалило домен из DNS, не отключив в админке — периодическая проверка переводит
  в 'failed' через сутки, уведомляет владельца, меню продолжает работать на основном домене.
- Кто-то направил свой домен на твой IP без добавления в систему — nginx не должен отдавать чужое
  меню. Обработай default_server явно.
- Домен уже используется другим заведением — ошибка на этапе добавления, не на этапе выпуска.
- Кириллические домены — принимать, но хранить в punycode.

DEFINITION OF DONE: домен добавляется, проверяется, получает сертификат, меню открывается по нему,
админка на нём недоступна, SEO-теги указывают на кастомный домен.
```

## Промт 4.1 — Бэкапы и восстановление

```
Задача: сделать автоматические бэкапы БД и загруженных фото с проверяемым восстановлением.
Делать это до первого платящего клиента, а не после первой потери данных.

Контекст: проект живёт на выделенном сервере, фото хранятся локально в public/uploads/:venue_id/,
объектное хранилище не используется. Значит, фото — такая же критичная часть бэкапа, как БД.

────────────────────────────────
1. ЧТО БЭКАПИМ
────────────────────────────────
- PostgreSQL: полный логический дамп через pg_dump в формате custom (-Fc), сжатие включено.
- Каталог public/uploads: полный архив раз в неделю, ежедневно — инкремент (rsync с --link-dest
  или tar с исключением уже сохранённых файлов). Фото занимают больше места, чем БД,
  полный архив каждый день не нужен.
- Файл .env НЕ бэкапим в общее хранилище. Отдельно, зашифрованным, вручную.

────────────────────────────────
2. РАСПИСАНИЕ И РОТАЦИЯ
────────────────────────────────
- Ежедневно в 04:00 по Ташкенту.
- Хранение: 7 ежедневных, 4 еженедельных, 6 ежемесячных. Удаление старых автоматическое.
- Каждый бэкап сопровождается файлом манифеста: дата, размер, контрольная сумма sha256,
  версия схемы (последняя применённая миграция), количество заведений, позиций и файлов в uploads.
  Количества нужны, чтобы заметить бэкап пустой базы.
- Реализация: скрипт scripts/backup.sh плюс systemd timer. НЕ node-cron внутри приложения —
  бэкап не должен зависеть от того, жив ли Node-процесс.
- Второе место хранения обязательно: локальный диск плюс копия на внешнее хранилище (другой сервер
  по rsync/ssh). Бэкап на том же диске, что и БД, бэкапом не является.

────────────────────────────────
3. ПРОВЕРКА И ВОССТАНОВЛЕНИЕ
────────────────────────────────
- scripts/restore.sh: восстановление в отдельную базу с подтверждением, чтобы случайно не затереть
  продакшен. По умолчанию восстанавливает в базу с суффиксом _restore_test.
- Еженедельная автоматическая проверка: восстановить последний дамп в тестовую базу, выполнить
  контрольные запросы (количество заведений, позиций, целостность внешних ключей), удалить тестовую
  базу, отчитаться в Telegram. Непроверенный бэкап — не бэкап.
- Документировать в README пошаговую процедуру восстановления на чистом сервере, включая порядок:
  восстановить БД → восстановить uploads → проверить миграции → запустить.

────────────────────────────────
4. УВЕДОМЛЕНИЯ
────────────────────────────────
- Успешный бэкап: тихо, без сообщений, иначе владелец перестанет их читать.
- Неудачный бэкап: немедленный алерт в Telegram с текстом ошибки.
- Два неудачных подряд: повторный алерт с пометкой критичности.
- Еженедельная сводка: размер базы, размер uploads, динамика роста, дата последней успешной
  проверки восстановления.
- Место на диске меньше 20% — предупреждение. Меньше 10% — критический алерт.

────────────────────────────────
EDGE CASES
────────────────────────────────
- pg_dump зависает — таймаут 30 минут и убийство процесса с алертом.
- Диск заполнился во время бэкапа — частичный файл удаляется, старые бэкапы не трогаются
  до успешного создания нового. Порядок важен: сначала новый, потом удаление старых.
- Восстановление на другой версии PostgreSQL — зафиксируй версию в манифесте и предупреди
  в документации.
- Фото удалены, но есть в бэкапе — процедура частичного восстановления только uploads должна быть
  описана отдельно.
- Бэкап во время активной записи: pg_dump берёт согласованный снимок, но uploads могут измениться
  посреди копирования. Копируй uploads ПОСЛЕ дампа и допускай, что несколько свежих файлов
  попадут в следующий инкремент — это нормально, главное не терять старые.

DEFINITION OF DONE: бэкап создаётся по расписанию, лежит в двух местах, еженедельная проверка
восстановления проходит и отчитывается, процедура восстановления описана и хотя бы раз пройдена руками.

# 5. Порядок и зависимости

Строгие зависимости:

- **0.1** — до всего остального.
- **0.2** — до любой задачи, добавляющей текстовые поля (2.1, 2.2, 3.1).
- **1.1** — до 1.2, 1.3, 1.4, 1.5, 2.4, 3.3, 4.1, 4.2 (всё, что шлёт уведомления).
- **1.2 → 1.3 → 1.4** — воронка целиком, строго в этом порядке.
- **2.1** — до 2.2 (карточка блюда показывает опции) и до 2.4 (заказ содержит опции).
- **2.4** требует 1.1 и создаёт столы, которые нужны 3.4 (QR по столам).
- **3.6** лучше делать до 3.7, иначе маршрутизацию по хосту придётся переписывать.
- **4.1** и **4.2** можно делать параллельно в любой момент после 1.1.

Рекомендуемая последовательность:

```
0.1 → 0.2 → 1.1 → 1.2 → 1.3 → 1.4 → 1.5 → 1.6 → 4.1 → 3.1 → 2.1 → 2.2
    → 3.2 → 2.4 → 3.4 → 3.3 → 2.3 → 3.5 → 2.5 → 4.2 → 3.6 → 3.7
```

Логика такая: сначала фундамент, потом воронка целиком (иначе продавать нечем), потом бэкапы (до первых денег), потом импорт (снимает нагрузку с тебя), дальше ценность для гостя и заведения, инфраструктурные вещи в конце.

Если нужно сократить до минимума, при котором сервис можно продавать: **0.1, 1.1, 1.2, 1.3, 1.4, 1.6, 4.1**. Всё остальное — усиление.

# 6. Что делаешь руками, а не промтом

- **Условия использования и политика конфиденциальности.** Написать, положить на сайт, указать ссылки в `site_settings`. К моменту первых оплат они нужны.
- **Проверка QR на дешёвом Android.** Не полагайся на отчёт агента — распечатай и отсканируй сам.
- **Пробное восстановление из бэкапа.** Один раз пройти процедуру руками на чистой машине.
- **Вопрос с ИП.** Без него Click и Payme недоступны, а приём оплаты на личную карту ограничивает тебя заведениями, которые платят из кармана и не проводят это как расход. Стоит заложить переход в первые месяцы.
- **Тестовое заведение на проде.** Заведи одно реальное кафе как пилот и пройди с ним весь путь до оплаты, прежде чем запускать регистрацию для всех.

# 7. Как пользоваться файлом

1. Открой нужный промт.
2. Скопируй сначала блок «Общие правила» (раздел 2), затем текст промта.
3. Вставь агенту одним сообщением.
4. Дождись плана, проверь список файлов и схему БД, подтверди.
5. После выполнения прогони `npm run migrate:up`, затем `migrate:down`, затем снова `up` — это ловит половину проблем с миграциями.
6. Проверь edge cases из промта вручную, а не по отчёту агента.
